# RFC-0005: Luna Volume Namespace and Drive Mapping

| Field | Value |
|---|---|
| RFC | 0005 |
| Название | Luna Volume Namespace and Drive Mapping |
| Статус | **Draft — revised 2026-10-07** |
| Цель | Project Luna Alpha |
| Связанные компоненты | luna-device-manager, luna-volume-manager, luna-root-mapping, luna-namespace, luna-security |
| Связанный проект | Windows System for Luna |

---

## 1. Аннотация

RFC-0005 определяет отдельную семантику хранения Luna, в которой физические
разделы не представляются приложениям как единое Linux-дерево путей.

Linux kernel по-прежнему предоставляет один VFS namespace как технический
substrate. Luna не обязана менять этот механизм на первом этапе. Вместо этого
Luna вводит собственный **Volume Namespace** и рассматривает диски, разделы и
тома как отдельные именованные объекты.

Пользователь видит:

```text
Disk 0
├── EFI                 [system/hidden]
├── LUNA-SYS            [system/hidden]
├── C:  LUNA-DATA      [persistent data]
└── SWAP                [swap/hidden]
```

После подключения внешних томов:

```text
C:  Luna Data
D:  USB Storage
E:  Backup
F:  Another Volume
```

Буква является **логическим пользовательским alias**, а не идентификатором
физического устройства и не Linux mountpoint.

---

## 2. Цели

Luna Volume Namespace MUST:

1. отделять identity тома от его пользовательской буквы;
2. отделять label от identity и от буквы;
3. предоставлять фиксированный `C:` для физического `LUNA-DATA`;
4. назначать внешним томам `D:`...`Z:` последовательно при подключении;
5. освобождать динамическую букву после отключения;
6. позволять пользователю явно переназначать букву;
7. позволять пользователю закрепить preferred letter для конкретного тома;
8. не требовать от приложения знания `/dev/sdX`, `/dev/nvmeXnY` или Linux mountpoint;
9. предоставлять одной и той же модели хранения потребителям Luna-native и
   Windows System for Luna;
10. работать независимо от того, находится ли LUNA-DATA на том же физическом
    диске, что EFI/LUNA-SYS, или на другом диске.

---

## 3. Не является целью

RFC не заменяет:

- Linux VFS;
- файловую систему;
- GPT/partition discovery;
- `luna-device-manager`;
- `luna-volume-manager`;
- `luna-root-mapping`;
- security authorization;
- Windows filesystem semantics.

Буква диска не означает, что Luna должна создать реальный Linux mount
`/d` или `/mnt/d`.

---

## 4. Термины

### Disk

Физическое устройство хранения. Имеет стабильную machine-level identity.

### Volume

Пользовательски доступная файловая область, обычно соответствующая GPT
partition + filesystem.

### VolumeId

Внутренний стабильный идентификатор объекта Volume. При наличии GPT основной
identity SHOULD использовать partition GUID; filesystem UUID и device identity
могут использоваться как дополнительные признаки проверки.

### VolumeLabel

Пользовательское имя тома. Label не является identity.

### DriveLetter

Короткий пользовательский alias `C`...`Z`. Alias не является identity.

### VolumeRef

Ссылочное значение для других Luna-компонентов. Оно указывает на VolumeId,
а не на Linux pathname.

### VolumePath

Luna-native путь **не содержит drive letter**. Он является структурированным
ссылочным значением:

```text
VolumePath {
    volume: VolumeRef,
    relative_path: "/projects/luna"
}
```

Человекочитаемое представление в native UI/CLI может использовать native
volume name, например:

```text
data:/projects/luna
backup:/documents/report.pdf
```

Это только отображение. Native API передаёт `VolumeRef + relative_path`, а не
строку `data:` и не Linux `/dev/...` path.

Windows compatibility layer может отобразить тот же объект как:

```text
C:\projects\luna
D:\documents\report.pdf
```

Такой путь не обязан напрямую передаваться Linux syscall `open(2)`.

---

## 5. Каноническое представление системного диска

Каноническая структура:

```text
Disk
├── EFI
├── LUNA-SYS
├── LUNA-DATA
└── SWAP
```

Правила:

- EFI является boot infrastructure и не получает обычную drive letter.
- LUNA-SYS является OS/system storage и не получает обычную drive letter.
- LUNA-DATA получает и сохраняет `C:` как специальный Luna alias.
- SWAP является storage resource без filesystem namespace и не получает букву.
- Другие пользовательские тома не получают специальных букв только из-за своей
  файловой системы или расположения.

LUNA-SYS не становится `S:` по умолчанию. Оно остаётся системным объектом,
доступным только компонентам, которым разрешён system-storage capability.

---

## 6. Стабильная identity против динамической буквы

Это центральное правило RFC.

```text
VolumeId       = identity
VolumeLabel    = user-facing name
DriveLetter    = current logical alias
PreferredLetter= optional explicit user preference
```

Автоматическое назначение внешних томов **не выполняется по GUID**.

При подключении:

1. `luna-device-manager` обнаруживает физический раздел и его metadata;
2. публикует `DiscoveredBlockVolume` для `luna-volume-manager`;
3. Volume Manager применяет auto-attach policy: поддерживаемый пользовательский filesystem становится `Available`;
4. для доступного внешнего тома проверяется explicit preferred letter;
5. если preferred letter не свободна или не задана — назначается первая свободная буква от `D` до `Z`;
6. assignment хранится только в runtime state; durable preferences сохраняются отдельно;
7. attach/update/detach events отражают новое состояние Volume Namespace.

Поэтому один и тот же USB-том может получить `D:` сегодня и `E:` после
следующего подключения, если пользователь специально не закрепил букву.

Это сознательно отличается от модели, где hardware identity автоматически
определяет букву.

---

## 7. Пользовательская перенастройка

Пользователь может:

- изменить label;
- изменить текущую букву;
- закрепить preferred letter;
- снять preferred letter;
- просматривать текущую identity и состояние тома.

`C:` для LUNA-DATA не переназначается.

Если preferred letter занята:

- нельзя молча отобрать её у другого активного тома;
- нельзя молча менять буквы нескольких томов;
- система выбирает свободную динамическую букву;
- пользователь получает состояние конфликта и может повторить assignment
  явно.

## 8. Persistent volume registry

Пользовательские preferences относятся к storage registry под:

```text
LUNA-DATA/system/volumes/
```

Предлагаемая форма:

```text
LUNA-DATA/system/volumes/
└── volume-registry.toml
```

Пример:

```toml
version = 1

[[volumes]]
id = "partition-guid:..."
label = "Backup"
preferred_letter = "E"

[[volumes]]
id = "partition-guid:..."
label = "Work"
preferred_letter = "D"
```

Registry хранит только durable user preferences и metadata. Текущие
динамические assignments находятся в RAM.

LUNA-DATA itself is always the special `C:` volume and does not depend on this
registry for initial availability.

---

## 9. Ответственность компонентов

### luna-device-manager

Владеет физическим discovery, sysfs/udev hardware metadata и kernel hotplug events.
Он публикует `DiscoveredBlockVolume` и не назначает drive letters, не хранит
пользовательские preferences и не определяет application access.

### luna-volume-manager

Владеет VolumeId/VolumeRef registry, logical attach/detach lifecycle,
auto-attach policy, label/native-name preferences и runtime drive-letter aliases.
Поддерживаемые файловые системы автоматически становятся логически доступными
без глобального host mount; неизвестные файловые системы и системные роли не
получают внешнюю букву. Компонент не заменяет `luna-namespace` при создании
application-specific mount instances.

Право приложения читать/писать том по-прежнему решает `luna-security`.

### luna-root-mapping

Не должен хранить сырые Linux `PathBuf` как архитектурный source identity.

Вместо этого mapping должен ссылаться на:

```text
SystemImageSource
VolumeRef
UserRef
BundleRef
DeviceRef
```

Например:

```text
logical /data
    -> VolumeRef(C:)

logical /home/luna
    -> UserRef(luna)

logical /usr/bin/editor
    -> BundleRef(editor@1.2)
```

### luna-security

Решает, разрешён ли доступ к VolumeRef, scope и access mode.

### luna-namespace

Материализует разрешённый MappingPlan в Linux namespace. Только этот слой
должен знать конкретные Linux mountpoints, bind mounts и device nodes.

## 10. Native Volume Namespace

Luna не должна делать из физических томов скрытую часть одного глобального
`/mnt` дерева. Том является самостоятельным объектом storage, а не просто
каталогом, в который кто-то выполнил `mount`.

Native presentation:

```text
Volumes
├── data        -> LUNA-DATA
├── Backup      -> attached volume
├── USB         -> attached volume
└── Work        -> attached volume
```

Для `LUNA-DATA` native name по умолчанию — `data`. Для внешнего тома native
name обычно выводится из его label и может быть переименован пользователем.

Эта коллекция `Volumes` является логическим интерфейсом Luna. Запись
`data:/projects/luna` означает `VolumeRef(LUNA-DATA) + /projects/luna`; это не
обязано означать наличие каталога `/data` на глобальном Linux root.

Windows presentation поверх того же объекта:

```text
This PC
├── C:  Luna Data
├── D:  Backup
├── E:  USB
└── F:  Work
```

`C:`/`D:`/`E:` — compatibility aliases и могут изменяться независимо от
VolumeId и native name.

---

## 11. Отдельный mount instance

Volume identity и mount state — разные сущности.

```text
Volume
  id = partition-guid:...
  label = "Backup"
  native_name = "backup"
  windows_preferred_letter = "E"

MountInstance
  volume = VolumeRef(...)
  namespace = ApplicationInstance
  state = Mounted
```

Luna не обязана иметь глобальный mountpoint вида `/mnt/backup`.

Когда конкретному namespace требуется файловый доступ, `luna-namespace`
получает разрешённый `VolumeRef` и создаёт отдельный Linux mount instance
внутри этого namespace. Внутренний mountpoint является implementation detail
и не входит в application API.

Для двух приложений один и тот же Volume может быть материализован в разные
namespace одновременно:

```text
VolumeRef(backup)
       +--------------------+
       |                    |
   App A namespace      App B namespace
       |                    |
   /data/...             /media/backup/...
```

Физический том при этом остаётся одним storage object; появляются только
отдельные namespace-specific mount instances.

Глобальный `/mnt` и глобальные bind mounts не являются частью архитектуры.

## 12. Как связаны Volume Namespace и Root Mapping

Volume Namespace отвечает на вопрос **«какие Volume существуют и как они
идентифицируются?»**.

Root Mapping отвечает на вопрос **«какой Volume или другой источник нужен
этому конкретному execution environment и по какому логическому пути?»**.

```text
Volume Namespace
      |
   VolumeRef
      |
      v
MappingPlan
      |
      v
luna-security
      |
      v
luna-namespace
      |
      v
namespace-local Linux mount
```

Поэтому `luna-root-mapping` не должен хранить `/dev/sdb1`, `/mnt/usb` или
другой физический pathname как источник identity. Он хранит типизированную
ссылку на Volume.

Пример:

```text
logical path: /data/projects
source: VolumeRef(LUNA-DATA) + /projects

logical path: /media/backup
source: VolumeRef(backup) + /documents
```

Конкретный Linux mountpoint для этих mappings выбирается только при
materialization namespace.

## 13. Native Luna path и Windows path

Native API:

```text
VolumePath {
    volume: VolumeRef,
    relative_path: "/projects/luna"
}
```

Native UI/CLI:

```text
data:/projects/luna
```

Windows compatibility:

```text
C:\projects\luna
```

Все три представления указывают на один storage object, но имеют разный
уровень семантики. Изменение Windows letter не меняет native path identity.

---

## 14. Applications

Application launch должен использовать тот же объектный storage model.

```text
ApplicationRef
    ↓
ApplicationPlan
    ↓
MappingPlan
    ↓
VolumeRef / SystemImageSource / UserRef / BundleRef
    ↓
luna-security
    ↓
AuthorizedApplicationPlan
    ↓
luna-namespace
    ↓
exact executable + namespace-local resources
```

System applications также разрешаются как именованные Luna objects. Обход
`/bin` и выбор «первого найденного ELF» не являются application model.

BusyBox может оставаться compatibility provider, но запуск applet должен быть
следствием явного mapping/application declaration, а не универсальным
fallback.

---

## 15. Windows System for Luna

Windows System for Luna MUST reuse the same Volume Namespace.

```text
                    Volume Namespace
                           |
             +-------------+-------------+
             |                           |
        Luna native                 Windows System
        presentation                compatibility
             |                           |
     VolumeRef + path              DriveLetter + path
             |                           |
             +-------------+-------------+
                           |
                     same Volume object
```

Windows-specific code owns NT path semantics and Windows application behavior,
but it does not rediscover the physical disk and does not invent a second
VolumeId database.

For Windows:

```text
C: -> VolumeRef(LUNA-DATA)
D: -> current external assignment
E: -> current external assignment
```

Dynamic external letters are assigned at attach time from the free `D..Z`
range, unless the user's persistent preference for that Volume is available.

---

## 16. Recovery

Recovery MUST be able to operate without physical LUNA-DATA.

The Recovery DATA Image is represented as a `RecoveryVirtual` Volume provider,
not as fake physical hardware:

```text
VolumeRef(recovery-data)
    role = RecoveryVirtual
    physical = none
    provider = Recovery DATA Image
```

Physical LUNA-DATA remains a separate Volume object when it is discoverable.
Recovery can therefore inspect the unavailable physical volume without making
it the source of the running logical root.

## 17. Security invariants

1. Knowing a DriveLetter does not grant access.
2. Knowing a VolumeId does not grant access.
3. Native volume name does not grant access.
4. Volume identity and authorization are separate.
5. Device nodes never become the application storage API.
6. An application receives only explicitly authorized VolumePath scopes.
7. Removing a volume revokes active mappings to it.
8. Reassignment of a letter does not transfer authorization from one VolumeId
   to another.
9. A MountInstance is namespace-local and does not make the volume globally
   visible to every application.

---

## 18. Required implementation changes


1. Keep VolumeId, native label/name, and active mount state separate.
2. Keep the logical Volume registry, preferences and drive aliases in `luna-volume-manager`; C: is reserved for LUNA-DATA and D..Z are dynamic external aliases.
3. Add attach/detach events carrying VolumeRef, label, role, capabilities, availability and current Windows alias. **Prototype implemented in `luna-volume-manager`; block discovery reconciliation emits Attached/Updated/Detached events and auto-attaches supported filesystems.**
4. Refactor luna-root-mapping so a mapping source can be a typed VolumeRef + relative path; raw Linux paths remain backend-only.
5. Make luna-namespace resolve authorized VolumeRef sources into namespace-local Linux mounts. No global /mnt storage tree is required. **Prototype implemented:** `VolumeMountResolver` + `VolumeMountManager` support file and directory targets, keep backend mountpoints outside the application root, constrain secure binds to source/destination roots, and enforce read-only mappings. `luna-security` distinguishes exact `VolumePath` grants from explicit `VolumeSubtree` grants.
6. Add the native Volumes API used by the file manager and other Luna applications.
7. Persist only user preferences such as label/native name and preferred Windows letter in LUNA-DATA/system/volumes/; active assignments remain runtime state.
8. Replace hardcoded executable discovery with SystemComponent/ApplicationRef resolution and explicit resource mappings.
9. Reuse the same Volume Namespace from Windows System for Luna.

No step requires replacing Linux VFS. Linux mounts remain an implementation mechanism below the Luna storage abstraction.

---

## 19. File manager and user presentation

The file manager SHOULD expose a virtual Volumes collection rather than deriving storage entries from /mnt or /dev.

Each entry is an object with at least:

~~~text
VolumeRef
label
native_name
role
filesystem
availability
mount state
Windows drive alias (when applicable)
~~~

Example native presentation:

~~~text
Volumes
├── data       Luna Data      [mounted]
├── Backup     ext4           [mounted]
└── USB        vfat           [mounted]
~~~

The native name is presentation metadata, not identity. Changing it must not alter VolumeId. The file manager can open a VolumeRef and a relative path directly through the Luna storage API; it does not need to construct /mnt paths.

## 20. Acceptance tests

The minimum acceptance suite SHOULD prove:

### Storage objects

- EFI, LUNA-SYS, LUNA-DATA and SWAP are discovered as separate storage roles;
- LUNA-DATA is always represented as native data and Windows C:;
- LUNA-SYS and SWAP have no ordinary Windows drive alias;
- one external volume receives D: and the next receives E:;
- removing an external volume releases its dynamic letter;
- a later external attach may reuse the released letter;
- a persistent preferred letter is honored when free;
- label/native-name changes never change VolumeId.

### Mounting and mapping

- a volume can exist in Detected/Available state without being mounted;
- mounting produces a separate MountInstance;
- no global /mnt hierarchy is required;
- MappingPlan refers to VolumeRef + relative path;
- each application namespace can materialize the same Volume independently;
- removing a Volume invalidates its active mappings cleanly.

### Applications

- system runtime is resolved by SystemComponent identity;
- user applications are resolved by ApplicationRef;
- application launch never scans /bin to choose an executable;
- BusyBox is exposed only through explicit compatibility mapping.

### Windows System for Luna

- Windows C: resolves to the same Luna VolumeRef used by native Luna;
- external Windows letters come from the shared Luna registry;
- Windows does not perform independent physical disk discovery.

---

## 21. Open implementation questions

These remain deliberately open until implementation evidence exists:

- exact filesystem support matrix for external volumes;
- exact VolumeId derivation for non-GPT media;
- whether native name is always derived from label or is a separate persistent preference;
- policy for read-only/removable/optical volumes;
- production IPC/API for Volumes queries and attach/detach notifications (a status file currently exists for diagnostics);
- exact native API spelling for VolumePath;
- exact internal mount backend and lifetime model for MountInstance;
- user-facing label and Windows-letter editor.

These questions must not cause the native storage model to fall back to a global Linux mount tree.
