# RFC-0005: Luna Volume Namespace and Drive Mapping

| Field | Value |
|---|---|
| RFC | 0005 |
| Название | Luna Volume Namespace and Drive Mapping |
| Статус | **Draft** |
| Цель | Project Luna Alpha |
| Связанные компоненты | luna-device-manager, luna-root-mapping, luna-namespace, luna-security |
| Связанный проект | Windows System for Luna |

---

## 1. Аннотация

RFC-0005 определяет отдельную семантику хранения Luna, в которой физические
разделы не представляются приложениям как единое Linux-дерево путей.

Linux kernel по-прежнему предоставляет один VFS namespace как технический
substrate. Luna не обязана менять этот механизм на первом этапе. Вместо этого
Luna вводит собственный **Volume Namespace** и рассматривает диски, разделы и
тома как отдельные именованные объекты.

Пользователь видит:

```text
Disk 0
├── EFI                 [system/hidden]
├── LUNA-SYS            [system/hidden]
├── C:  LUNA-DATA      [persistent data]
└── SWAP                [swap/hidden]
```

После подключения внешних томов:

```text
C:  Luna Data
D:  USB Storage
E:  Backup
F:  Another Volume
```

Буква является **логическим пользовательским alias**, а не идентификатором
физического устройства и не Linux mountpoint.

---

## 2. Цели

Luna Volume Namespace MUST:

1. отделять identity тома от его пользовательской буквы;
2. отделять label от identity и от буквы;
3. предоставлять фиксированный `C:` для физического `LUNA-DATA`;
4. назначать внешним томам `D:`...`Z:` последовательно при подключении;
5. освобождать динамическую букву после отключения;
6. позволять пользователю явно переназначать букву;
7. позволять пользователю закрепить preferred letter для конкретного тома;
8. не требовать от приложения знания `/dev/sdX`, `/dev/nvmeXnY` или Linux mountpoint;
9. предоставлять одной и той же модели хранения потребителям Luna-native и
   Windows System for Luna;
10. работать независимо от того, находится ли LUNA-DATA на том же физическом
    диске, что EFI/LUNA-SYS, или на другом диске.

---

## 3. Не является целью

RFC не заменяет:

- Linux VFS;
- файловую систему;
- GPT/partition discovery;
- `luna-device-manager`;
- `luna-root-mapping`;
- security authorization;
- Windows filesystem semantics.

Буква диска не означает, что Luna должна создать реальный Linux mount
`/d` или `/mnt/d`.

---

## 4. Термины

### Disk

Физическое устройство хранения. Имеет стабильную machine-level identity.

### Volume

Пользовательски доступная файловая область, обычно соответствующая GPT
partition + filesystem.

### VolumeId

Внутренний стабильный идентификатор объекта Volume. При наличии GPT основной
identity SHOULD использовать partition GUID; filesystem UUID и device identity
могут использоваться как дополнительные признаки проверки.

### VolumeLabel

Пользовательское имя тома. Label не является identity.

### DriveLetter

Короткий пользовательский alias `C`...`Z`. Alias не является identity.

### VolumeRef

Ссылочное значение для других Luna-компонентов. Оно указывает на VolumeId,
а не на Linux pathname.

### VolumePath

Luna-native путь вида:

```text
C:/projects/luna
D:/documents/report.pdf
```

Это семантика Luna API. Такой путь не обязан напрямую передаваться Linux
syscall `open(2)`.

---

## 5. Каноническое представление системного диска

Каноническая структура:

```text
Disk
├── EFI
├── LUNA-SYS
├── LUNA-DATA
└── SWAP
```

Правила:

- EFI является boot infrastructure и не получает обычную drive letter.
- LUNA-SYS является OS/system storage и не получает обычную drive letter.
- LUNA-DATA получает и сохраняет `C:` как специальный Luna alias.
- SWAP является storage resource без filesystem namespace и не получает букву.
- Другие пользовательские тома не получают специальных букв только из-за своей
  файловой системы или расположения.

LUNA-SYS не становится `S:` по умолчанию. Оно остаётся системным объектом,
доступным только компонентам, которым разрешён system-storage capability.

---

## 6. Стабильная identity против динамической буквы

Это центральное правило RFC.

```text
VolumeId       = identity
VolumeLabel    = user-facing name
DriveLetter    = current logical alias
PreferredLetter= optional explicit user preference
```

Автоматическое назначение внешних томов **не выполняется по GUID**.

При подключении:

1. `luna-device-manager` обнаруживает Volume;
2. получает его VolumeId и свойства;
3. проверяет пользовательскую explicit preference;
4. если preferred letter разрешена и свободна — назначает её;
5. иначе выбирает первую свободную букву от `D` до `Z`;
6. регистрирует assignment только в active runtime state;
7. уведомляет заинтересованные Luna-компоненты.

Поэтому один и тот же USB-том может получить `D:` сегодня и `E:` после
следующего подключения, если пользователь специально не закрепил букву.

Это сознательно отличается от модели, где hardware identity автоматически
определяет букву.

---

## 7. Пользовательская перенастройка

Пользователь может:

- изменить label;
- изменить текущую букву;
- закрепить preferred letter;
- снять preferred letter;
- просматривать текущую identity и состояние тома.

`C:` для LUNA-DATA не переназначается.

Если preferred letter занята:

- нельзя молча отобрать её у другого активного тома;
- нельзя молча менять буквы нескольких томов;
- система выбирает свободную динамическую букву;
- пользователь получает состояние конфликта и может повторить assignment
  явно.

---

## 8. Persistent volume registry

Пользовательские preferences относятся к storage registry под:

```text
LUNA-DATA/system/volumes/
```

Предлагаемая форма:

```text
LUNA-DATA/system/volumes/
└── volume-registry.toml
```

Пример:

```toml
version = 1

[[volumes]]
id = "partition-guid:..."
label = "Backup"
preferred_letter = "E"

[[volumes]]
id = "partition-guid:..."
label = "Work"
preferred_letter = "D"
```

Registry хранит только durable user preferences и metadata. Текущие
динамические assignments находятся в RAM.

LUNA-DATA itself is always the special `C:` volume and does not depend on this
registry for initial availability.

---

## 9. Ответственность компонентов

### luna-device-manager

Владеет:

- discovery физических devices;
- discovery volumes;
- add/remove lifecycle;
- VolumeId;
- filesystem/device capabilities;
- active DriveLetter assignments;
- persistent volume preferences через `system/volumes`.

Он не решает, имеет ли конкретное приложение право читать том.

### luna-root-mapping

Не должен хранить сырые Linux `PathBuf` как архитектурный source identity.

Вместо этого mapping должен ссылаться на:

```text
SystemImageSource
VolumeRef
UserRef
BundleRef
DeviceRef
```

Например:

```text
logical /data
    -> VolumeRef(C:)

logical /home/luna
    -> UserRef(luna)

logical /usr/bin/editor
    -> BundleRef(editor@1.2)
```

### luna-security

Решает, разрешён ли доступ к VolumeRef, scope и access mode.

### luna-namespace

Материализует разрешённый MappingPlan в Linux namespace. Только этот слой
должен знать конкретные Linux mountpoints, bind mounts и device nodes.

---

## 10. Почему это лучше обычного mount tree

Обычная Linux модель может выглядеть так:

```text
/
├── boot
├── etc
├── home
├── mnt
│   ├── disk1
│   └── usb
└── usr
```

В Luna это не является архитектурной моделью storage.

Модель Luna:

```text
Volume Namespace
├── C:  -> LUNA-DATA
├── D:  -> attached volume
├── E:  -> attached volume
└── ...

Logical Application Namespace
├── /usr/...
├── /home/...
├── /data/...
└── ...
```

Первое отвечает на вопрос **«какие хранилища существуют?»**.

Второе отвечает на вопрос **«какие ресурсы видит этот конкретный процесс?»**.

Они связаны Root Mapping, но не являются одним namespace.

---

## 11. Luna-native VolumePath

Native Luna APIs SHOULD представлять путь как структурированное значение:

```text
VolumePath {
    volume: VolumeRef,
    relative_path: "/projects/luna"
}
```

Строковое `C:/projects/luna` является UI/CLI representation.

Это позволяет:

- менять букву без изменения identity;
- передавать VolumeRef между процессами;
- проверять authorization до materialization;
- не давать приложению raw kernel paths.

---

## 12. POSIX compatibility

Legacy Linux applications требуют обычные POSIX paths.

Для них Luna runtime materializes отдельный namespace:

```text
Luna VolumePath
      ↓
MappingPlan
      ↓
security
      ↓
luna-namespace
      ↓
POSIX logical path
```

Например:

```text
C:/documents/a.txt
       ↓
VolumeRef(C) + /documents/a.txt
       ↓
authorized mapping
       ↓
/app-instance/data/documents/a.txt
```

Конкретный internal mountpoint не является частью приложения и может
изменяться между execution environments.

---

## 13. Приложения и запуск

Это RFC должно закрыть текущую проблему с моделью:

```text
/bin/busybox
     ↓
запускаем то, что нашли
```

Вместо этого canonical application launch:

```text
AppId / ComponentId
        ↓
ApplicationRef
        ↓
resolve Bundle or System Component
        ↓
ApplicationPlan
        ↓
MappingPlan
        ↓
luna-security
        ↓
AuthorizedApplicationPlan
        ↓
luna-namespace
        ↓
exact executable
```

System application также является именованным Luna object.

Например:

```text
SystemComponent
  id = "luna-system-runtime"
  version = "0.1.0"
  source = SystemImage
  executable = "apps/luna-system-runtime/luna-system-runtime"
```

Таким образом `busybox` может существовать как compatibility provider, но он
не является универсальным fallback и не определяет application model Luna.

---

## 14. Windows System for Luna

Windows System for Luna MUST consume the same Volume Namespace rather than
inventing an independent physical-disk identity layer.

Windows-specific mapping becomes:

```text
Windows C:
    -> Luna VolumeRef(C)

Windows D:
    -> Luna VolumeRef(D)
```

The Windows subsystem may maintain its own NT path and permission semantics,
but physical discovery and user-facing Luna volume assignment remain owned by
the Luna storage model.

This gives Luna one hardware/storage identity layer and multiple execution
namespaces:

```text
                 Volume Namespace
                        |
          +-------------+-------------+
          |                           |
     Luna POSIX                  Windows System
     namespace                   namespace
```

---

## 15. Recovery

Recovery MUST be able to operate when physical LUNA-DATA is unavailable.

Therefore Recovery receives a VirtualData provider from the Recovery DATA Image.

The Volume Namespace should represent this as a provider object, not as fake
physical hardware.

Example:

```text
Recovery VirtualData
    -> VolumeRef(recovery-data)
    -> internal alias, not C:
```

Physical LUNA-DATA remains a separate volume object when it is discovered.

---

## 16. Security invariants

1. Knowing a DriveLetter does not grant access.
2. Knowing a VolumeId does not grant access.
3. Volume identity and authorization are separate.
4. Device nodes never become the application storage API.
5. An application receives only explicitly authorized VolumePath scopes.
6. Removing a volume revokes active mappings to it.
7. Reassignment of a letter does not transfer authorization from one VolumeId to
   another.

---

## 17. Required implementation changes

The first implementation should be incremental:

1. introduce `VolumeRef`, `VolumeLabel`, `DriveLetter` and a volume registry;
2. move dynamic letter assignment into `luna-device-manager`;
3. keep `C:` permanently attached to physical LUNA-DATA;
4. add attach/detach events carrying Volume identity and current letter;
5. refactor `luna-root-mapping` from `PhysicalPath` to typed source references;
6. make `luna-namespace` the only layer that resolves source references to Linux
   mount paths;
7. add native `VolumePath` APIs;
8. replace hardcoded system executable paths with SystemComponent/ApplicationRef
   resolution;
9. use the same Volume Namespace from the future Windows System for Luna.

No step requires replacing Linux VFS first.

---

## 18. Acceptance tests

The minimum acceptance suite SHOULD prove:

### Storage

- EFI, LUNA-SYS, LUNA-DATA and SWAP are discovered as separate Volume/Storage
  roles;
- LUNA-DATA is always `C:`;
- LUNA-SYS has no ordinary drive letter;
- SWAP has no filesystem path;
- one external volume receives `D:`;
- attaching another receives `E:`;
- removing `D:` frees D;
- attaching another volume later may reuse `D:`;
- changing a letter does not change VolumeId;
- preferred letter survives reboot/re-discovery only when explicitly pinned.

### Mapping

- `C:/...` resolves to a VolumeRef rather than a raw Linux pathname;
- mappings remain namespace-local;
- security can deny a volume without changing its identity;
- a removed volume invalidates mappings cleanly.

### Application launch

- system runtime is resolved by SystemComponent identity;
- user application is resolved by ApplicationRef;
- no application launch depends on scanning `/bin`;
- BusyBox is available only where an explicit compatibility mapping grants it.

### Windows

- Windows System for Luna can bind a Windows drive to an existing Luna VolumeRef;
- Windows does not need to rediscover physical disks independently.

---

## 19. Open implementation questions

These intentionally remain open until implementation evidence exists:

- exact filesystem support matrix for external volumes;
- exact VolumeId derivation for non-GPT media;
- policy for read-only/removable/optical volumes;
- exact representation of unavailable or offline volumes;
- GUI/API used to edit labels and preferred letters;
- exact native API spelling for VolumePath;
- whether Luna shell should accept `C:/...` directly or only a higher-level path
  object/API.

These are implementation questions, not reasons to collapse the Volume Namespace
back into Linux mount paths.
