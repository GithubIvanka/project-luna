## 1. Abstract

Project Luna is an operating system built around the Linux kernel. It is **not**
a conventional Linux distribution. Luna defines its own user-visible storage
model, boot architecture, system-image model, namespace composition, management
boundaries and recovery architecture, while reusing Linux kernel mechanisms where
useful.

This RFC establishes the architectural foundation:

- purpose and guiding principles;
- the four-layer conceptual model (EFI → BOOT → SYSTEM → DATA);
- the four physical storage areas (EFI / SYSTEM / DATA / SWAP);
- the boot architecture and fallback model;
- the system/data separation;
- the immutable, versioned system-image model;
- the independent kernel model;
- the top-level component architecture.

---

## 2. Motivation

Luna is inspired by the **One File Linux** idea:

> the system should have a very small, stable and maximally immutable foundation.

Conventional Linux distributions accumulate a large number of top-level
directories, mutable system files, tightly coupled kernel/system updates, and
package managers that scatter application files across `/`. Luna deliberately
avoids this model.

Luna must **not** be:

- a regular Linux distribution with a changed package set and theme;
- a Docker-like operating system;
- a system with a large number of top-level root directories;
- a system where every application installs files across `/`;
- a system where updating the kernel requires rewriting the whole OS;
- a system where updating the OS destroys user data;
- a system where the user must manually mount USB drives via the terminal;
- a system where the bootloader rewrites boot state on every launch;
- a system where all kernels are tried without compatibility checks;
- a system where a System Image is a `.lbp` bundle.

---

## 3. Guiding Principles

The following principles are **Accepted**:

1. **Small system foundation.** The core is minimal and stable.
2. **Maximum immutability.** System Images are immutable in normal operation.
3. **Versioned System Images.** Each OS version is a distinct, addressable image.
4. **Independent system/kernel updates.** Updating the system does not require
   updating the kernel, and vice versa.
5. **Applications as bundles.** Applications are immutable bundles (`.lbp`).
6. **Isolated dependencies.** Dependencies are addressable and isolated, not
   merged into one global heap of conflicting files.
7. **Minimal top-level directories.** The user-visible layout is small and clear.
8. **Custom Luna bootloader.** `luna-boot.efi` owns the boot decision path.
9. **Automatic external device management.** Removable media appear automatically
   in the desktop without manual `mount` commands.
10. **Application isolation via existing Linux mechanisms.** Mount namespaces are
    the primary isolation primitive; Luna does not build its own container OS.
11. **Single management tool.** The `luna` CLI is the primary system-management
    interface (a thin client over backend services).
12. **Recoverability.** The system can recover from a failed update.
13. **User data independence.** User data does not depend on a specific System
    Image version.

## 4. The Four-Layer Conceptual Model

The whole project can be held in mind through four conceptual layers
(section 96):

```
EFI      → launches
BOOT     → decides what to launch
SYSTEM   → contains versioned OS images and kernels
DATA     → contains everything mutable
```

| Layer | Responsibility |
|-------|----------------|
| **EFI** | Provides the execution environment and launches the bootloader. |
| **BOOT** | Decides which kernel and System Image to launch (`luna-boot.efi`). |
| **SYSTEM** | Stores versioned System Images and versioned kernels. |
| **DATA** | Stores everything mutable: apps, drivers, libs, volumes, users, cache. |

> **Distinction.** The four *conceptual layers* (EFI → BOOT → SYSTEM → DATA) are
> not the same as the four *physical storage areas* (EFI / SYSTEM / DATA / SWAP).
> BOOT is a logical layer implemented by `luna-boot.efi`, which physically lives
> in the EFI area.

## 5. Physical Storage Model

### 5.1 Four physical areas (Accepted)

The installed machine has four physical areas (section 105.1):

```
EFI      — bootloader storage; hidden from ordinary users
SYSTEM   — immutable/versioned OS images and kernels; hidden from ordinary users
DATA     — mutable user-visible storage
SWAP     — optional swap policy; may be absent, a swap file/partition, and/or ZRAM
```

### 5.2 Canonical disk structure (Accepted)

```
Disk
 │
 ├── EFI
 │   └── Luna/
 │       └── luna-boot.efi
 │
 ├── SYSTEM
 │   ├── images/
 │   │   ├── <version>.squashfs
 │   │   ├── <version>.toml
 │   │   └── ...
 │   └── kernels/
 │       ├── <kernel>
 │       └── ...
 │
 ├── DATA                (Btrfs, user-visible)
 │   ├── system/
 │   │   ├── apps/
 │   │   ├── drivers/
 │   │   ├── libs/
 │   │   ├── volumes/
 │   │   └── config/
 │   ├── users/
 │   │   └── <user>/
 │   │       ├── home/
 │   │       ├── data/
 │   │       └── config/
 │   └── cache/
 │
 └── SWAP / ZRAM         (policy-driven)
```

### 5.3 User-visible DATA layout (Accepted)

The ordinary user sees DATA as:

```
DATA/
├── system/
│   ├── apps/       — installed application bundles
│   ├── drivers/    — drivers
│   ├── libs/       — managed shared libraries/dependencies
│   ├── volumes/    — managed external-volume representations
│   └── config/     — system-wide mutable configuration
├── users/
│   └── <user>/
│       ├── home/     — Documents, Downloads, ...
│       ├── data/     — mutable application data for this user
│       └── config/   — user/application configuration
└── cache/
```

Rules:

- There must be no duplicate parallel trees (`data/apps`, `portable`, etc.)
  created merely for organizational purposes.
- `DATA/system` is the OS-managed mutable system area.
- Every local user has exactly three top-level directories: `home/`, `data/`,
  `config/`.
- The normal logical application home is `/home/<user>/`. Access to another
  user's home is not granted by default.

### 5.4 File manager views (Accepted direction)

The file manager may expose dedicated **Apps** and **Volumes** views:

- Apps is backed by `DATA/system/apps`.
- Volumes is backed by `DATA/system/volumes` and presents friendly volume names
  rather than raw `/dev` paths.

## 6. Boot Architecture

### 6.1 Bootloader (Accepted)

Luna uses its own minimal UEFI bootloader:

```
EFI/Luna/luna-boot.efi
```

Functionality directly related to the UEFI boot flow belongs in
`luna-boot.efi`. The model is:

```
UEFI
 ↓
luna-boot.efi
 ↓
Linux kernel
 ↓
Luna System Image
```

`luna-boot.efi` must remain small. It must **not** become a full userspace OS,
manage the GUI, do package management, manage applications, or become `lunad`.

### 6.2 Normal boot (Accepted)

Normal boot is direct and unobtrusive:

```
Power → UEFI → luna-boot.efi → compatible Linux kernel → Luna System Image
```

The user should not see a long boot menu, unnecessary messages or delays.

### 6.3 Boot Menu (Accepted)

The Boot Menu is invoked only by a deliberate user action: pressing **B** during
startup.

```
Power → UEFI → luna-boot.efi
                 │
                 ├── B not pressed → normal boot
                 └── B pressed     → Boot Menu
```

The Boot Menu must allow:

- selecting a System Image;
- selecting a compatible kernel;
- entering Recovery;
- booting from USB/another external medium;
- other system recovery/boot operations.

### 6.4 Boot path and DATA attach (Accepted)

```
UEFI
  ↓
luna-boot.efi
  ↓
boot-state / current
  ↓
compatible kernel
  ↓
compatible System Image
  ↓
logical root
  ↓
DATA attach
  ↓
normal user sessions
```

At boot, Luna first establishes a minimal RAM/virtual logical root. Only after
that foundation exists does it attempt to attach DATA. This ordering allows the
system to enter Recovery when DATA is unavailable.

### 6.5 `current` and `factory` (Accepted semantics)

- `current` identifies the current working System Image + kernel combination.
  It may change.
- `factory` identifies the original guaranteed-good installation (Factory System
  Image + Factory Kernel). It is never deleted or modified by normal
  update/cleanup operations.

> **Open.** The exact physical format of `current` and `factory` is not yet
> defined (section 68). Separate persistent boot-state metadata is maintained so
> the bootloader can change boot decisions without requiring normal userspace
> access.

### 6.6 Kernel compatibility (Accepted)

The bootloader must not enumerate all installed kernels. It reads the selected
System Image's manifest to obtain the set of compatible kernels and offers only
those.

Fallback must respect compatibility: an image is only tried against its
compatible kernels. After exhausting compatible kernels, the bootloader may move
to another System Image.

### 6.7 Fallback model (Accepted)

```
current
  └── working → continue
  └── failed
        ↓
      compatible kernel / image fallback
        ↓
      ...
        ↓
      all normal combinations fail
        ↓
      factory
```

- A **System Image failure** may support *soft fallback* without a full machine
  reboot where technically safe (try an older compatible image with the current
  kernel).
- A **kernel panic** requires a reboot before selecting another kernel.
- Boot-state changes are **event-driven**, not rewritten on every ordinary boot.

> **Open.** The exact kernel-panic detection procedure and the exact soft-fallback
> procedure are not yet defined (section 68).

### 6.8 Recovery and Factory paths (Accepted)

Normal storage failure path:

```
Normal
  ↓ DATA unavailable
Recovery (RAM writable state + virtual recovery user)
  ↓ System Image unavailable
Factory (immutable original image + kernel)
```

Recovery is a fully working repair environment — not merely a read-only shell and
not Factory. It has a Recovery System Image, a compatible boot path, a virtual
temporary recovery user, and RAM-backed writable state. Recovery does not
automatically expose protected user data.

## 7. System/Data Separation (Accepted)

This is one of the most important architectural boundaries:

- **SYSTEM** is OS-managed, immutable/versioned, and hidden from ordinary users.
  It contains only `images/` and `kernels/`.
- **DATA** is mutable, user-visible, and holds applications, drivers, libraries,
  volumes, users and cache.

Consequences:

- System Images and kernels are **never** stored in DATA.
- System Images and kernels are updated through dedicated, privileged update
  paths, not by ordinary processes.
- User data lives in DATA and does not depend on a specific System Image
  version.

## 8. Immutable, Versioned System Image Model

### 8.1 System Image = SquashFS (Accepted invariant)

A System Image is a version of Luna itself. It is stored **directly as a
SquashFS image**:

```
SYSTEM/images/<version>.squashfs
```

Each System Image has its own manifest next to it:

```
SYSTEM/images/<version>.toml
```

This is a primary architectural invariant. A System Image is **not** a `.lbp`
bundle.

### 8.2 Why SquashFS (Accepted rationale)

SquashFS fits Luna because it is:

- read-only;
- compressed;
- suitable for versioned immutable system images;
- able to hold an entire system filesystem tree;
- able to separate the system filesystem from user data;
- suitable for loading only required parts on demand (hybrid/lazy loading).

### 8.3 Per-image manifest (Accepted invariant)

Every System Image has its **own** manifest. A single global manifest for all
images must not be the only source of information about images.

The manifest must at least conceptually describe: name, version, architecture,
format, compatible kernels, required boot parameters, and other information the
bootloader needs. This lets `luna-boot.efi` learn about an image without loading
the image itself.

> **Open.** The exact TOML System Image manifest format is not yet defined
> (section 68). Conceptual examples in the Source of Truth are illustrative only
> and must not be treated as an approved format.

### 8.4 Hybrid / lazy loading (Accepted semantics)

The System Image is the immutable source of system content, but it is not the
final runtime root. Luna creates a logical Linux-compatible root in RAM/virtual
filesystem state and materializes required system content into that runtime view.

Desired loading model:

```
System Image
     ↓
critical initial materialization
     ↓
RAM logical root
     ↓
manifest-informed prefetch
     ↓
demand-driven loading
```

Materialized system content can be reclaimed while the source System Image
remains available. If the source image is detached/deleted, all content required
for the continued running system must first be fully materialized and verified.

> **Open.** The exact kernel-level implementation of materialization/hybrid
> loading is intentionally left for implementation/specification (section 68).
> The architecture requires the semantics, not a premature commitment to one
> copy/cache mechanism.

## 9. Independent Kernel Model

### 9.1 Kernel storage (Accepted)

Kernels belong to SYSTEM and are stored in:

```
SYSTEM/kernels/<kernel>/
```

### 9.2 Independence of System Image and kernel (Accepted)

A fundamental decision:

- updating a System Image must not require updating the kernel;
- updating the kernel must not require rewriting the System Image.

This enables:

- rolling back the system;
- rolling back the kernel;
- testing a new kernel while keeping a working System Image;
- keeping a working kernel while updating the other part.

System Images and kernels have independent lifecycle and compatibility metadata.
A kernel is selected only when compatible with the chosen image.

> **Open.** The exact kernel metadata structure, versioning and compatibility
> format are not yet defined (section 68).

## 10. Bundle Model (foundation only)

> The full Bundle Format is specified separately in **RFC-0002**. This section
> states only the foundation-level invariants relevant to the baseline.

- Applications and other installable components use the **`.lbp`** Luna Bundle
  Format.
- `.lbp` is the **transport/archive** representation of a Bundle. It is **not**
  the runtime representation and it is **not** a System Image format.
- An installed application is an **immutable bundle**, independent from its
  mutable user data.
- Installed bundles live under `DATA/system/apps`. `DATA/system/apps` is the
  installed-app registry/view, not a requirement that every executable must
  physically remain there forever.
- Shared libraries are stored under `DATA/system/libs` and can be reused by
  multiple applications where compatible.

Two independent formats exist:

| Format | Used for |
|--------|----------|
| `.lbp` | Bundles (applications and other installable components) |
| `.squashfs` | Versioned System Images |

## 11. Top-Level Component Architecture

### 11.1 Component map (Accepted, Phase 1.3)

The architecture uses separate components where there is a real responsibility
boundary (section 105.23):

```
luna-cli
 │
 ├── luna-system-manager
 ├── luna-app-manager
 ├── luna-device-manager
 ├── luna-update-manager
 ├── luna-kernel-manager
 ├── luna-root-mapping
 ├── luna-security
 ├── luna-system-runtime
 ├── luna-app-runtime
 ├── luna-fs
 ├── luna-bundle
 ├── luna-config
 ├── luna-log
 └── luna-common
```

This is an architectural map, not a statement that every crate/daemon already
exists in the repository.

### 11.2 Ownership boundaries (Accepted)

- `luna-app-manager` owns application lifecycle (install/update/remove/verify/
  migrate/import). It does **not** own execution.
- `luna-app-runtime` owns application execution together with the system runtime.
- `luna-system-manager` owns the System State model/query layer.
- `luna-update-manager` executes System Image/kernel transactions.
- `luna-kernel-manager` owns kernel model/compatibility, but installation/
  update/removal is executed by `luna-update-manager`.
- `luna-root-mapping` is a narrow component that constructs the logical root and
  mappings. It must not absorb app lifecycle, session management, recovery or
  general system management.
- `luna-security` is the central policy authority. It does not own app lifecycle,
  namespace creation or filesystem mounting.
- `luna-common` must remain small and must not become a dumping ground.

### 11.3 Canonical launch chain (Accepted)

```
User / GUI / CLI
        ↓
luna-system-runtime
        ↓
UserSession
        ↓
luna-app-runtime
        ↓
ApplicationInstance
        ↓
Linux kernel
```

### 11.4 CLI architecture (Accepted direction)

The main executable is `luna-cli`. The CLI is a thin client over backend/service
APIs; GUI and CLI call the same backend rather than implementing separate
management logic.

> **Open.** The exact command set, permissions, output format and machine-readable
> mode of the CLI are not yet defined (section 68).

## 12. Security and Authority Foundation

> Detailed security contracts are consolidated in section 109 (Phase 1.5). This
> section states only the baseline invariants.

- There is **no permanent root user** and no required `sudo`/`su` privilege
  hierarchy. Administrative authority is a protected system capability.
- `luna-security` is the central permission/capability policy authority.
- The conceptual authorization model is:
  `Subject + Resource + Action + Context → PolicyDecision`.
- Integrity, Authenticity, Trust and Authorization are separate concepts.
- Users are isolated from one another by default.

> **Open.** Credential storage, recovery and authentication protocols remain open
> security-specification work.

- exact TOML Bundle manifest;
- exact TOML System Image manifest;
- exact `current` / `factory` physical format;
- exact kernel metadata structure;
- exact kernel-panic detection procedure;
- exact soft-fallback procedure;
- exact SquashFS RAM loading / hybrid loading implementation;
- exact application permission model;
- exact device automount backend;
- exact OpenRC/service integration;
- final `luna` CLI;
- exact runtime namespace structure;
- bundle/image signatures;
- cryptographic verification policy;
- update transaction protocol.

## 15. Rationale Summary

Luna's foundation rests on one central separation and a small set of invariants:

```
Project Luna
     ↓
 minimal immutable system foundation
     ↓
 Linux kernel
     ↓
 EFI / SYSTEM / DATA / SWAP
     ↓
 custom luna-boot.efi
     ↓
 versioned System Images (direct SquashFS)
     ↓
 one manifest per System Image
     ↓
 independent kernels + kernel compatibility
     ↓
 current / factory
     ↓
 soft fallback
     ↓
 .lbp bundles for applications/components
```

Everything mutable is pushed to DATA; everything versioned and immutable is kept
in SYSTEM; boot decisions are compatibility-aware and event-driven; and recovery
always has a guaranteed-good path back to Factory.
