# RFC-0003: Luna Platform

**Status:** Draft
**Target:** Project Luna Alpha
**Scope:** system platform contract, compatibility boundaries, audio, GUI, desktop services

## 1. Summary

Luna Platform is the system-level contract used by native Luna applications and
compatibility layers. Its purpose is to make application-facing behavior stable
while allowing the implementation of audio, graphics, desktop services, and
security to evolve independently.

The platform is a Luna-defined API boundary above the kernel-facing
implementation and below application/toolkit integrations.

## 2. Goals

Luna Platform MUST provide a stable contract for:

- audio services;
- window and desktop integration;
- settings and appearance;
- clipboard and data transfer;
- file selection dialogs;
- permission-gated resources;
- capability discovery.

The platform SHOULD make native Luna applications independent of a specific
audio server, GUI toolkit, compositor implementation, or desktop environment.

Existing applications SHOULD be supported through compatibility adapters rather
than becoming architectural dependencies of Luna.

## 3. Non-goals

Luna Platform does not define:

- a replacement Linux kernel;
- a general-purpose container manager;
- a second compositor inside the platform layer;
- a requirement that GTK or Qt be removed from the system;
- a requirement that every legacy application use Luna-native widgets.

## 4. Layer model

The intended model is:

    Application
         |
         +----------------------+---------------------+
         |                      |                     |
      Luna API                 GTK                    Qt
         |                      |                     |
         |                Luna integration      Luna integration
         |                      |                     |
         +----------------------+---------------------+
                                |
                         Luna Platform
                                |
        +-----------------------+------------------------+
        |                       |                        |
     Audio                 Desktop                Security
        |                   services                 |
        |                       |                        |
        +-----------------------+------------------------+
                                |
                         platform adapters
                                |
                       Wayland / kernel / devices

Wayland remains the window-system protocol and compositor-facing boundary. Luna
Platform does not require replacing the existing compositor used by the Luna
desktop. The current desktop can continue to use niri while Luna interfaces are
introduced incrementally.

## 5. Core design rule

Applications depend on Luna semantics, not implementation identity.

For example, the application asks for an output device, clipboard data, a file
selection, or a system setting. It does not need to know whether the underlying
implementation uses ALSA, PipeWire, a compatibility server, or another
backend.

The concrete implementation is selected below the Luna contract.

## 6. Audio architecture

The Luna-facing audio boundary is `luna-audio`.

The intended topology is:

    Application
         |
      Luna Audio API
         |
     luna-audio service
         |
      audio backend
         |
       ALSA / device

Compatibility adapters may sit between the service and existing application
protocols:

    PulseAudio application -> Pulse compatibility -> Luna audio service
    JACK application       -> JACK compatibility   -> Luna audio service

PipeWire may be used as an initial implementation bridge while the Luna-native
service is developed. Such use is an implementation detail and MUST NOT leak
into the Luna application contract.

ALSA remains the lowest-level hardware-facing audio boundary in the initial
architecture. The Luna service owns policy such as endpoint discovery, volume,
mute state, routing, and permissions.

## 7. Audio invariants

The Luna audio contract MUST:

1. expose stable Luna endpoint identities;
2. distinguish input and output endpoints;
3. keep application APIs independent from a specific audio server;
4. allow backend replacement without changing native clients;
5. provide a clear place for permissions and policy;
6. avoid making direct hardware ownership part of the application API.

The service SHOULD support per-application streams later, but the first
implementation may start with endpoint discovery and control.

## 8. GUI architecture

GTK and Qt are application UI toolkits, not interchangeable window-system
protocols. Luna therefore integrates with them at their platform boundaries
instead of attempting to emulate their internals in one universal server.

The intended structure is:

    Luna application
         |
      Luna UI SDK
         |
      Luna Platform
         |
      Wayland

    GTK application
         |
      GTK / GDK + Luna integration
         |
      Luna Platform / Wayland

    Qt application
         |
      Qt + Luna platform/style integration
         |
      Luna Platform / Wayland

For Qt, the initial integration point is the Qt platform abstraction boundary
and related theme integration. For GTK, the integration points include its
Wayland/GDK backend, settings, styling, and desktop portals.

## 9. What Luna can standardize

Luna SHOULD standardize the user-facing platform behavior that toolkits can
consume consistently:

- system color scheme;
- accent color;
- fonts and metrics where supported;
- icons;
- clipboard behavior;
- drag-and-drop semantics;
- file dialogs;
- notifications and desktop actions;
- permissions;
- settings discovery;
- application lifecycle integration.

Luna cannot force an arbitrary application that draws custom pixels to expose
individual buttons, lists, or other widgets to the platform. Visual consistency
for legacy applications is therefore achieved through toolkit integration,
theme contracts, and common desktop services rather than compositor-side
widget replacement.

## 10. Luna UI SDK

A native Luna UI toolkit is a separate layer from Luna Platform.

Luna UI will eventually provide canonical widgets and interaction patterns for
native applications. The initial platform work MUST NOT depend on the toolkit
being complete.

The long-term relationship is:

    Luna Platform = system behavior and services
    Luna UI       = native widgets and interaction model

This separation keeps the system contract usable by applications that do not
use the native Luna toolkit.

## 11. Desktop portals and permissions

Luna should expose permission-gated desktop operations through a portal-like
service boundary. Applications should not need unrestricted access to devices,
other applications' data, or host filesystem locations merely to perform a
normal desktop operation.

Examples include:

- opening or saving a user-selected file;
- microphone access;
- camera access;
- screen capture;
- clipboard transfer;
- opening a location with a default application.

The permission decision belongs to Luna policy, not to an individual toolkit.

## 12. Compatibility strategy

Compatibility is implemented as adapters around a stable Luna contract.

Conceptually:

    Legacy API
        |
    Compatibility layer
        |
    Luna contract
        |
    Luna implementation

The adapter MUST translate semantics, not duplicate the entire subsystem.

This principle is especially important for audio because PulseAudio and JACK
clients can continue to exist while the Luna service owns the canonical policy.

## 13. Initial component boundaries

The initial workspace direction is:

    components/luna-platform
    components/luna-audio

Future components may include:

    luna-portal
    luna-ui-core
    luna-ui-wayland
    luna-gtk
    luna-qt

A future component name does not imply that the component must be implemented
immediately. Boundaries are recorded here to prevent subsystem responsibilities
from becoming mixed together.

## 14. Initial API boundary

`luna-platform` currently defines version and capability discovery types plus a
minimal backend boundary. It MUST remain free of toolkit and compositor-specific
dependencies.

`luna-audio` defines backend-neutral audio concepts and the `AudioBackend` trait.
It MUST NOT require a concrete audio server in its public API.

IPC, daemon lifetime, process supervision, and backend selection remain
implementation details outside the data-model crates.

## 15. Development phases

### Phase 1 — contracts

- establish `luna-platform` crate;
- stabilize capability discovery;
- establish backend-neutral `luna-audio` types;
- document subsystem ownership.

### Phase 2 — service skeletons

- create the Luna audio service process;
- add service IPC boundary;
- add mock audio backend;
- add backend selection and capability reporting.

### Phase 3 — compatibility

- connect the first Linux audio implementation;
- add PulseAudio compatibility;
- evaluate JACK compatibility requirements;
- keep existing desktop audio usable during migration.

### Phase 4 — desktop integration

- define settings contract;
- define clipboard contract;
- define portal and permission contract;
- integrate GTK and Qt desktop behavior.

### Phase 5 — native UI

- implement `luna-ui-core`;
- define canonical Luna widgets;
- build native Luna applications against the same platform contract.

## 16. Testing requirements

Every backend implementation MUST have contract tests that exercise the same
Luna-facing behavior.

Compatibility layers MUST be tested independently from the native service.

The test suite SHOULD verify that replacing one backend with another does not
change the behavior observed through the Luna contract.

## 17. Current implementation state

This RFC is paired with the initial `luna-platform` crate.

The existing `luna-audio` crate has been adjusted on this branch so that its
public contract is backend-neutral. PipeWire/WirePlumber can remain part of the
initial system implementation while the Luna-native service is developed.

No compositor replacement is required for this work.

## 18. Open technical work

The next implementation work is to define the Luna audio IPC protocol, service
lifecycle, endpoint identity rules, stream model, and backend adapter interface.

After the audio service boundary is stable, the same platform principles should
be applied to settings, portals, clipboard, and toolkit integrations.
