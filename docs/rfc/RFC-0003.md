## 1. Аннотация

RFC-0003 определяет архитектуру локальной сети вычислительных узлов,
на которой Luna Agent может работать без облачного LLM API.

Цель — отделить оркестрацию разработки от места выполнения inference.
Репозиторий и безопасность рабочего дерева остаются под контролем Luna Agent,
а модель может работать на этом же ПК или на другом ПК в локальной сети.

```text
Luna Agent
   |
   +-- local model node A
   |
   +-- local model node B
   |
   `-- optional cloud worker
```
## 2. Базовая реализация

Первым runtime локального inference предлагается `llama.cpp` с OpenAI-compatible
HTTP API. Он поддерживает GGUF и позволяет использовать CPU/GPU одной машины.
Конкретный backend не является частью ABI Luna Agent: его можно заменить,
если сохраняется совместимый API.

Для компактного coding worker кандидатом является Ornith-1.5-9B.
Официальный GGUF-репозиторий публикует Q4_K_M около 5.78 GB и MIT-лицензию.
Модель также доступна в Q5/Q6/Q8 и BF16 вариантах.

Ornith-1.5-9B позиционируется авторами как модель для reasoning, coding и
agentic tasks. В опубликованной авторами оценке она получила 47.0 на
Terminal-Bench 2.1 и 70.6 на SWE-bench Verified; эти результаты относятся
к их описанной экспериментальной конфигурации и не гарантируют такую же
производительность на локальном ПК.

## 3. Роли узлов

`Coordinator` — машина с Luna Agent, Git checkout и policy контроля.

`Inference Node` — машина, предоставляющая только LLM API. Она не получает
доступ к Git автоматически и не должна самостоятельно менять репозиторий.

`Reviewer Node` — отдельный inference endpoint с другой моделью или другим
checkpoint. Он используется для независимой проверки результата.

Для первой реализации достаточно Coordinator + один Inference Node.
## 4. Сеть

Узлы соединяются по обычной изолированной LAN/Wi-Fi сети.
Coordinator обращается к inference endpoint по фиксированному локальному
адресу/имени. Интернет для inference не требуется.

Для offline режима DNS, package repositories и внешние tool endpoints
не являются обязательными. Модель, tokenizer, runtime и необходимые
ресурсы должны быть заранее размещены на локальных узлах.

```text
                 local LAN
        +---------------------------+
        |                           |
 Coordinator                 Inference Node
 Luna Agent                  llama.cpp server
        |                           |
        +------ OpenAI API ---------+
```

## 5. Разделение данных и инструментов

Модельный узел получает только prompt/context, который Coordinator решил
передать ему. Git checkout, credentials и физические диски проекта на
Inference Node не монтируются и не расшариваются по умолчанию.

Команды и изменения файлов выполняются агентом на Coordinator. Это позволяет
использовать даже недоверенный или экспериментальный local checkpoint как
reasoning worker без выдачи ему прямого доступа к рабочей среде.

Для будущего multi-node execution может появиться отдельный controlled
executor, но он не входит в первую версию RFC.

## 6. Два ПК

Рекомендуемая первая схема для Luna:

```text
PC-1
  Luna Agent
  Git checkout
  Harness/OpenCode
        |
        | LAN / HTTP
        v
PC-2
  llama.cpp
  Ornith-1.5-9B или другая local model
```

После проверки стабильности можно добавить второй inference endpoint:

```text
             +--> PC-2: local coding model
Luna Agent -+
             `--> PC-3: independent review model
```
## 7. Лимиты

Локальная модель устраняет внешнюю API-квоту и зависимость от количества
токенов облачного провайдера. Это не означает бесконечный контекст:
ограничениями остаются context window модели, RAM/VRAM, скорость inference,
диск и время выполнения.

Для длинной работы Luna Agent должен хранить состояние задачи во внешнем
state и делать новые AI-turns, а не пытаться удерживать весь проект в одном
контексте.

## 8. Безопасность

Offline означает отсутствие необходимости во внешнем LLM API, но не
автоматическую безопасность локальной сети. Inference endpoint должен быть
доступен только из доверенной LAN, без port forwarding во внешний интернет.

Luna Agent сохраняет обязательные барьеры: одна рабочая ветка, чистое дерево
перед новой задачей, lock runner, fingerprint между AI-turns, verification
после commit и запрет destructive host/disk operations.

## 9. Эволюция

Следующий этап может добавить `worker registry`, health-check endpoint,
планирование по возможностям узлов и автоматический failover между local
models. Это не меняет task contracts и не позволяет узлам напрямую владеть
Git checkout.

RFC-0003 пока является архитектурным предложением. Реальное подключение
второго ПК выполняется после определения его CPU, RAM и GPU и проверки
локального inference runtime.
