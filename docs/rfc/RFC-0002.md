## 1. Abstract

This RFC proposes **Bundle Format v1**, the `.lbp` format used to package
applications and other installable components in Project Luna.

`.lbp` is the **transport/archive** representation of a Bundle. It is **not** the
System Image format (System Images are direct SquashFS images) and it is **not**
the runtime representation of an installed application.

This document proposes:
- an outer container layout;
- a TOML manifest schema;
- a payload model;
- identity and versioning;
- dependency declarations;
- capability requests;
- logical-interface (mapping) declarations;
- integrity and a signature extension point;
- compatibility, storage and lifecycle rules (format aspects).

---

## 2. Goals and Non-Goals

### 2.1 Goals

- Define a portable, self-describing container for Luna Bundles.
- Allow reading and validating the manifest **without extracting the payload**.
- Support integrity verification and a future signature path.
- Declare dependencies, requested capabilities and the logical interface.
- Keep the format simple and Rust-friendly.

### 2.2 Non-Goals

This RFC does **not** define:

- the System Image format (that is SquashFS + per-image manifest, separate spec);
- the runtime/installed representation in full (only the boundary with it);
- application permission *enforcement* (owned by `luna-security`, section 109.1);
- namespace construction (owned by `luna-root-mapping` / runtime, sections 105.4, 109.2);
- the update transaction protocol (section 68);
- the final `luna` CLI surface.

---

## 3. Relationship to other formats

Two independent formats exist (sections 12, 32, 105.8):

| Format | Used for | Payload kind |
|--------|----------|--------------|
| `.lbp` | Bundles (applications and other installable components) | transport/archive container |
| `.squashfs` | Versioned System Images | direct SquashFS filesystem image |

Critical invariants preserved:

- A System Image is **never** a `.lbp` bundle (section 72, 105.8).
- `.lbp` is the transport/archive representation, **not** the runtime
  representation (section 108.3).
- An installed application is an **immutable bundle**, independent from its
  mutable user data (section 105.8, 108.4).

---

## 4. Terminology

| Term | Meaning |
|------|---------|
| **Bundle** | A packaged, immutable unit of installable software. |
| **`.lbp`** | The transport/archive file that carries a Bundle. |
| **Manifest** | The TOML metadata describing the Bundle. |
| **Payload** | The actual file content of the Bundle (binaries, resources). |
| **ApplicationID** | Stable identity of an application (section 108.1). |
| **BundleID** | Identity of a concrete bundle/build (section 108.1). |
| **Installed bundle** | The runtime representation under `DATA/system/apps`. |

---

## 5. Accepted invariants this RFC builds on

These are already **Accepted** in the Source of Truth and are restated here only
as anchors (not re-decided):

- `.lbp` is the Bundle Format; System Image is SquashFS (sections 12, 32, 105.8).
- Installed bundles are immutable; overrides are separate user-data hooks, not
  payload mutation (section 108.4).
- Applications declare requested capabilities; declarations are requests, not
  grants (section 108.5).
- Identity is layered: ApplicationID / BundleID / Version / ApplicationInstanceID /
  UserID (section 108.1).
- Shared libraries live under `DATA/system/libs` and are reused where compatible;
  missing dependencies are reported and require user consent before external
  download (section 105.26).
- Bundles describe a **logical interface**, not absolute DATA paths (section 109.5).
- `luna-app-manager` owns lifecycle (install/update/remove/verify/migrate/import);
  it does not own execution (sections 105.9, 109.6).
- External package formats (`.deb`/`.rpm`) may be ingested and converted into
  Luna Bundles on a best-effort basis (section 108.3).
- Trust, signature validity and permission are separate concepts (sections 108.7,
  109.1).
- Modified/overridden bundles enter a non-original trust state and must warn the
  user (section 108.4).

## 6. Container format — `PROPOSAL`

> Everything in this section is a **proposal** for discussion.

### 6.1 Design goals for the container

1. Read the manifest without extracting the whole payload.
2. Verify integrity per section.
3. Reserve a clean signature block.
4. Stay simple enough to implement early.

### 6.2 Proposed outer layout

```
.lbp file
┌──────────────────────────────────────────────┐
│ Header (fixed size)                          │
│   magic            : "LBP1"  (4 bytes)       │
│   format_version   : u16 LE  (= 1)           │
│   flags            : u16 LE                  │
│   section_count    : u32 LE                  │
│   section_table_off: u64 LE                  │
│   header_hash      : 32 bytes                │
├──────────────────────────────────────────────┤
│ Section table (section_count entries)        │
├──────────────────────────────────────────────┤
│ MANIFEST section   (TOML, uncompressed)      │
├──────────────────────────────────────────────┤
│ PAYLOAD section    (compressed file tree)    │
├──────────────────────────────────────────────┤
│ RESOURCES section  (optional, compressed)    │
├──────────────────────────────────────────────┤
│ SIGNATURE section  (optional)                │
└──────────────────────────────────────────────┘
```

### 6.3 Proposed section-table entry

Each entry (fixed size) describes one section:

```
section_type        : u32 LE   (1=manifest, 2=payload, 3=resources, 4=signature)
compression         : u32 LE   (0=none, 1=zstd)
offset              : u64 LE   (absolute byte offset in file)
compressed_length   : u64 LE
uncompressed_length : u64 LE
content_hash        : 32 bytes (see 6.5)
```

### 6.4 Rationale

- A fixed header + section table lets `luna-app-manager` read and validate the
  manifest and hashes **before** touching the (possibly large) payload.
- Per-section hashes support integrity checks and future incremental verification.
- An explicit signature section avoids the circular problem of signing an archive
  that contains its own signature.

### 6.5 Hash algorithm — `PROPOSAL, needs decision`

Candidates: **BLAKE3** (fast, good Rust support) or **SHA-256** (wide compatibility).
This is a decision point; nothing is chosen yet.

### 6.6 Alternative considered — `PROPOSAL`

A simpler alternative is `.lbp` = `tar.zst` archive with the manifest at a known
member path. It is easier to build with existing tools but makes the signature
block and "read manifest without full extraction" less clean. The structured
container in 6.2 is the primary proposal; the tar-based variant is recorded as the
fallback option pending decision.

## 7. Manifest schema — `PROPOSAL`

> The manifest is TOML (section 45, where TOML is appropriate). The schema below
> is a **proposal**; field names and required/optional status need approval.

### 7.1 Proposed manifest

```toml
# Luna Bundle Format v1 — manifest.toml
format = 1

[bundle]
id       = "org.example.firefox"   # ApplicationID (stable)
name     = "Firefox"               # display name (may change)
version  = "141.0.0"               # see 7.4
type     = "application"           # see 7.3

[platform]
arch        = "x86_64"
min_system  = "1.0.0"              # minimum compatible System Image (proposal)

[entry]
exec    = "bin/firefox"            # path inside payload
logical = "/usr/bin/firefox"       # logical path exposed to the app (109.5)

# Dependencies are bundle identities + version constraints (105.26)
[[dependency]]
id      = "org.luna.libs.gtk"
version = "^4.0.0"

[[dependency]]
id      = "org.luna.libs.openssl"
version = ">=3.0.0"

# Requested capabilities — requests only, NOT grants (108.5)
[capabilities]
requested = [
  "network",
  "filesystem.user-documents.read",
  "clipboard",
]

# Logical interface / mapping declarations (109.5)
[[mapping]]
logical = "/usr/bin/firefox"
source  = "bin/firefox"
access  = ["execute"]

[[mapping]]
logical = "/libs/gtk"
source  = "@dep:org.luna.libs.gtk"
access  = ["read"]

[metadata]
author   = "Example"
license  = "MPL-2.0"
homepage = "https://example.org"
```

### 7.2 Field-by-field

| Field | Required | Notes |
|-------|----------|-------|
| `format` | yes | Bundle Format version (here `1`). Lets Luna reject unknown formats. |
| `bundle.id` | yes | Stable ApplicationID. Must not change across versions. |
| `bundle.name` | yes | Display name; may change. |
| `bundle.version` | yes | See 7.4. |
| `bundle.type` | yes | See 7.3. |
| `platform.arch` | yes | Target architecture. |
| `platform.min_system` | no | Proposed minimum System Image compatibility. Needs alignment with System Image/kernel compatibility model. |
| `entry.exec` | yes (application) | Entry point inside payload. |
| `entry.logical` | no | Logical exposed path (109.5). |
| `[[dependency]]` | no | Bundle dependencies. |
| `[capabilities].requested` | no | Requested capabilities (never grants). |
| `[[mapping]]` | no | Logical interface declarations. |
| `[metadata]` | no | Author/license/homepage. |

### 7.3 `bundle.type` — `PROPOSAL, needs decision`

Candidate primary type: `application`.

Other candidate types (`library`, `runtime`, `driver`, `theme`, `font`) are
**not decided**. In particular:

- `system` / System Image is **excluded** — System Images are SquashFS, not
  bundles (section 72, 105.8).
- Whether `driver` is a bundle type or a separate entity under
  `DATA/system/drivers` needs a separate decision (section 36).

### 7.4 Versioning — `PROPOSAL, needs decision`

Proposed: **Semantic Versioning** `MAJOR.MINOR.PATCH`. Not yet accepted; needs
explicit confirmation and alignment with version comparison rules.

### 7.5 Identity model (anchors to 108.1)

- `bundle.id` corresponds to the stable **ApplicationID**.
- A concrete build's **BundleID** is proposed to bind identity + version + content
  hash (see 9.2), supporting the trust-binding requirement of section 108.4.
- `ApplicationInstanceID` and `UserID` are runtime concepts and are **not** part
  of the manifest.

### 7.6 Capabilities vocabulary — `PROPOSAL, needs alignment`

The capability names in `[capabilities].requested` are placeholders. The actual
vocabulary must be aligned with the `luna-security` model (section 109.1) and is
**not** finalized here. Declarations are requests only (section 108.5).

## 8. Payload — `PROPOSAL`

### 8.1 Structure

The payload section carries the bundle's file tree. Proposed packaging: a
compressed archive (e.g. `tar.zst`) of:

```
payload/
├── bin/        # executables
├── lib/        # private libraries (if not shared)
├── resources/  # data files, icons, locales
└── ...
```

### 8.2 Immutability

Once installed, the bundle payload is immutable (section 108.4). Customization is
expressed through controlled overrides in user data, validated by the policy
layer — never by mutating the payload.

### 8.3 Logical interface

The payload is addressed by **logical** paths declared in `[[mapping]]` /
`[entry]`, not by absolute DATA paths (section 109.5). The application must not
need to know whether its physical payload lives under `DATA/system/apps`, an
external disk, or removable media (section 105.8).

---

## 9. Integrity — `PROPOSAL`

### 9.1 Hashes

Each section carries a `content_hash` in the section table (6.3). Verification
proceeds: header → section table → manifest hash → payload hash. A mismatch
rejects the whole bundle (no partial install).

### 9.2 BundleID and content binding

Proposed: **BundleID = f(ApplicationID, version, payload content hash)**.
This supports section 108.4 ("local trust binds to the specific content
identity/hash"). Exact derivation is a decision point.

---

## 10. Signatures — `EXTENSION POINT / PROPOSAL`

Signature infrastructure is an architectural extension point (sections 108.7,
109.1). This RFC reserves a SIGNATURE section but does **not** commit to an
algorithm or trust policy.

Constraints already accepted elsewhere:

- signature validity ≠ trust ≠ permission (section 108.7, 109.1);
- a valid signature does not automatically grant execution;
- Integrity / Authenticity / Trust / Authorization are separate (section 109.1).

Algorithm (e.g. Ed25519) and verification policy are **open**.

---

## 11. Compatibility — `PROPOSAL`

- `format = 1` identifies Bundle Format v1.
- A Luna implementation encountering an unknown `format` must reject the bundle
  rather than guess.
- Backward/forward compatibility rules are a decision point.

---

## 12. Storage rules — `PROPOSAL`

- A `.lbp` **file** is a transport artifact (downloaded, copied, on removable
  media). It is not required to remain after installation.
- The **installed bundle** lives under `DATA/system/apps` as the installed-app
  registry/view (sections 105.1, 105.8).
- Applications stored outside `DATA/system/apps` (e.g. on removable media) may be
  launched directly and optionally registered so they appear in the Apps view
  (section 105.8).
- Multiple versions of the same application may coexist when identities/versions
  permit (section 105.8).

---

## 13. Lifecycle (format aspects) — `PROPOSAL`

Lifecycle **procedures** are owned by `luna-app-manager` (sections 105.9, 109.6).
This RFC states only the format-relevant expectations:

- **Install:** validate header → manifest → hashes → (optional signature) →
  extract/register into `DATA/system/apps`.
- **Update:** install new version alongside old; do not destroy a working older
  version merely because an update exists (section 105.8). Data migration is
  orchestrated by `luna-app-manager` with a mandatory checkpoint (section 108.2).
- **Remove:** remove the immutable bundle; mutable user data handling follows
  retention rules and may prompt the user (section 105.11).

The exact transaction protocol is **not** defined here (section 68).

---

## 14. Package ingestion note (anchors to 108.3)

`.deb` / `.rpm` may be ingested and converted into Luna Bundles with generated
Luna manifest metadata, on a best-effort basis. Import scripts are analyzed in a
restricted environment; unsupported behaviors are reported, not silently granted
system access. The conversion mapping is out of scope for this RFC.

---

## 15. Open questions / needs decision

The following must be explicitly decided before this RFC can be Accepted:

1. Container choice: structured container (6.2) vs `tar.zst` (6.6).
2. Hash algorithm: BLAKE3 vs SHA-256 (6.5).
3. `bundle.type` taxonomy and whether `driver` is a bundle type (7.3).
4. Versioning scheme and comparison rules (7.4).
5. BundleID derivation (9.2).
6. Capability vocabulary (aligned with `luna-security`) (7.6).
7. `platform.min_system` semantics vs System Image/kernel compatibility model.
8. Compression choice for payload/resources.
9. Forward/backward compatibility policy (11).
