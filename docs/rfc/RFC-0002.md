> **Authority note.** This document records the decisions accepted for Bundle
> Format v1 during Phase 1.6. The `.lbp` format is the transport/archive
> representation of a Luna Bundle. It is not the System Image format and it is
> not the runtime representation of an installed application.

---

## 1. Abstract

RFC-0002 defines **Bundle Format v1**, the `.lbp` transport/archive format used
for Project Luna application and component bundles.

The format is deliberately separate from:

- the SquashFS-based System Image format;
- installed immutable Bundle storage;
- application runtime state;
- update transactions;
- Security policy enforcement.

The v1 format provides a deterministic, self-describing outer container with a
TOML manifest, deterministic payload, per-section integrity hashes, and an
optional Ed25519 signature section.

---

## 2. Goals

Bundle Format v1 MUST:

1. identify its format unambiguously;
2. allow manifest inspection before payload extraction;
3. provide deterministic representation suitable for stable content identity;
4. detect corruption and malformed section metadata before installation;
5. prevent archive path traversal and unsafe special entries;
6. support logical mapping declarations without exposing physical `DATA/...`
   paths;
7. support requested capabilities without granting permissions;
8. allow immutable installed Bundles to coexist across versions;
9. support optional authenticity through Ed25519 without conflating signature,
   trust, and authorization.

---

## 3. Non-Goals

This RFC does not define:

- System Image layout or SquashFS generation;
- namespace construction;
- application lifecycle orchestration;
- Security policy enforcement;
- update/rollback transactions;
- repository discovery protocol;
- delta update protocol;
- user-data backup format;
- final `luna` CLI syntax.

---

## 4. Relationship to Luna storage

`.lbp` is a **transport artifact**.

```text
.lbp
  ↓ inspect / verify / trust
Bundle
  ↓ install
DATA/system/apps/...
```

The installed Bundle payload is immutable. User configuration, user data and
cache remain outside the payload and follow Luna's established DATA layering.

An external Bundle may be launched from removable media after inspection,
integrity verification and the applicable trust/authorization decision. Its
identity does not depend on filename or physical location.

System Images are independent SquashFS artifacts and are never encoded as `.lbp`.

---

## 5. Terminology and identity

### 5.1 Bundle identity

The v1 representation carries:

```text
BundleId
Version
ContentIdentity
```

`BundleId` is the typed Luna identity used to identify the application/bundle.

`Version` uses Semantic Versioning:

```text
MAJOR.MINOR.PATCH
```

`ContentIdentity` is a BLAKE3-256 digest of the canonical Bundle content defined
by section 12.

The `.lbp` filename and physical storage location are not part of identity.

### 5.2 Version coexistence

Different versions of the same application are independent immutable Bundles.
They may coexist and be launched independently when otherwise compatible with
Luna runtime policy.

---

## 6. Outer container

### 6.1 Byte order

All integer fields are encoded **little-endian**.

### 6.2 Fixed header

The header is exactly **64 bytes**:

| Offset | Size | Field | Meaning |
|-------:|-----:|-------|---------|
| `0` | 4 | `magic` | ASCII `LBP1` |
| `4` | 2 | `version_major` | currently `1` |
| `6` | 2 | `flags` | v1 MUST be `0` |
| `8` | 4 | `section_count` | number of section entries |
| `12` | 8 | `section_table_offset` | absolute file offset |
| `20` | 8 | `section_table_length` | table length in bytes |
| `28` | 4 | `header_length` | MUST be `64` |
| `32` | 32 | `header_hash` | BLAKE3-256 of header with this field zeroed |

`version_major` is the format major version. A future minor-format mechanism is
not encoded as a separate header integer in v1; compatible evolution is governed
by the rules in section 18.

The parser MUST reject invalid magic, unsupported major version, non-zero unknown
flags, wrong header length, malformed table coordinates and arithmetic overflow.

### 6.3 Fixed section entries

Each section entry is exactly **64 bytes**:

| Offset | Size | Field |
|-------:|-----:|-------|
| `0` | 4 | `section_type` |
| `4` | 4 | `compression` |
| `8` | 8 | `offset` |
| `16` | 8 | `compressed_length` |
| `24` | 8 | `uncompressed_length` |
| `32` | 32 | `content_hash` |

Known section types are:

```text
1 = MANIFEST
2 = PAYLOAD
3 = RESOURCES
4 = SIGNATURE
```

Section rules:

| Section | Required | Compression |
|---------|----------|-------------|
| `MANIFEST` | exactly one | `NONE` |
| `PAYLOAD` | exactly one | `NONE` or `ZSTD` |
| `RESOURCES` | at most one | `NONE` or `ZSTD` |
| `SIGNATURE` | at most one | `NONE` |

Unknown section types are rejected in v1. Unknown sections can only become
forward-compatible through a future format revision that explicitly assigns the
semantics.

Section ranges MUST NOT overlap each other or the header/table region.

### 6.4 Section integrity

`content_hash` is BLAKE3-256 over the stored section bytes as present in the
container, before decompression. The reader MUST verify it before exposing the
decoded section contents.

---

## 7. Compression

v1 defines:

```text
0 = NONE
1 = ZSTD
```

Canonical writer policy:

```text
MANIFEST  → NONE
PAYLOAD   → ZSTD
RESOURCES → ZSTD when present
SIGNATURE → NONE
```

A writer generating a canonical Bundle MUST use this policy. A non-canonical
transport copy may use `NONE` for `PAYLOAD`/`RESOURCES` when the semantic Bundle
content remains unchanged; the parser must still validate the stored bytes and the
canonical ContentIdentity must be computed independently of transport compression.

---

## 8. Manifest

The manifest is mandatory TOML.

Canonical structure:

```toml
format = 1

[bundle]
id = "org.example.firefox"
name = "Firefox"
version = "141.0.0"
type = "application"

[platform]
arch = "x86_64"
min_system = "1.0.0"

[entry]
exec = "bin/firefox"
logical = "/usr/bin/firefox"

[[dependency]]
id = "org.luna.libs.gtk"
version = "^4.0.0"

[capabilities]
requested = ["network", "clipboard"]

[[mapping]]
logical = "/usr/bin/firefox"
source = "bin/firefox"
access = ["execute"]

[metadata]
author = "Example"
license = "MPL-2.0"
homepage = "https://example.org"
```

### 8.1 Required fields

Required:

```text
format
bundle.id
bundle.name
bundle.version
bundle.type
platform.arch
```

Application bundles require `[entry]` and `entry.exec`.

### 8.2 Bundle types

v1 permits:

```text
application
component
```

Unknown types are rejected.

System Images are not Bundle types.

### 8.3 Dependency constraints

Dependency version constraints use the restricted SemVer grammar implemented by
Luna. Unsupported syntax MUST be rejected rather than guessed.

### 8.4 Unknown fields

Unknown manifest fields may be preserved/ignored when they do not introduce an
unknown required semantic value. Unknown required semantics and unsupported
enumerated values MUST cause rejection.

---

## 9. Logical mappings and capabilities

Mappings are declarations of the Bundle's logical interface, not grants of
permission.

```toml
[[mapping]]
logical = "/usr/bin/firefox"
source = "bin/firefox"
access = ["execute"]
```

The manifest MUST NOT contain physical Luna storage paths such as
`DATA/system/apps/...` or `DATA/users/...` as mapping targets.

`logical` is a Linux-style absolute logical path. `source` is a Bundle-relative
path. Traversal and host-specific absolute source paths are invalid.

The optional `access` field describes requested access semantics. Final
authorization is performed by `luna-security` and runtime enforcement.

Requested capabilities are also requests only:

```toml
[capabilities]
requested = ["network", "clipboard"]
```

The presence of a capability declaration never grants that capability.

---

## 10. Dependencies and shared libraries

A Bundle may declare dependencies without embedding the dependency payload.
Dependency references can be satisfied from compatible Bundle-local resources,
`DATA/system/libs`, or other approved dependency sources.

Dependency resolution is owned by the application/install tooling, not by the
`.lbp` parser itself.

Shared library selection and physical storage are outside this RFC; the manifest
only expresses the logical/dependency contract.

---

## 11. Payload

`PAYLOAD` carries the Bundle file tree as a deterministic TAR stream, optionally
compressed as described by section 7.

Allowed TAR entries:

- regular files;
- directories.

Prohibited in v1:

- symbolic links;
- hard links;
- FIFOs;
- sockets;
- character/block devices;
- other special entry types.

Payload paths MUST be relative, canonical, traversal-free and confined to the
Bundle payload root. Duplicate payload paths are rejected.

Explicit directory entries are optional.

---

## 12. Determinism and ContentIdentity

Canonical payload construction MUST:

1. enumerate entries deterministically;
2. sort entries lexicographically by canonical Bundle-relative path;
3. use deterministic TAR metadata;
4. use `uid = 0` and `gid = 0` unless a future revision defines otherwise;
5. use canonical `mtime = 0`;
6. omit host-specific user/group names and device metadata;
7. omit access/change timestamps;
8. produce identical payload bytes for identical Bundle content.

Manifest bytes used for identity/signature MUST use canonical TOML serialization.
Formatting differences in semantically equivalent manifests MUST NOT create
multiple canonical identities.

`ContentIdentity` is:

```text
BLAKE3-256(
    canonical_manifest
    || canonical_payload
    || canonical_resources_if_present
)
```

It excludes `.lbp` filename, physical location, transport padding and signature
bytes.

`ContentIdentity` therefore remains unchanged when an `.lbp` file is renamed or
moved to another storage device.

---

## 13. Resource section

`RESOURCES` is optional and reserved for Bundle resources whose representation is
more useful outside the main executable/file-tree payload.

Its exact semantic resource registry is implementation-defined in v1 as long as
its bytes participate in ContentIdentity and follow the same path-safety and
integrity rules. A Bundle does not require a RESOURCES section when all resources
fit in PAYLOAD.

---

## 14. Signature

The `SIGNATURE` section is optional.

v1 defines **Ed25519** for Bundle signatures.

A signature record contains:

```text
algorithm
key_id
publisher_id
signature
```

The signed material is the canonical Bundle representation:

```text
canonical header
+
canonical section table
+
canonical MANIFEST bytes
+
PAYLOAD content identity
+
RESOURCES content identity, if present
```

The SIGNATURE section is excluded from its own signed material.

A missing signature is valid at the format level. Whether an unsigned Bundle can
be installed or launched is a Luna trust-policy decision.

A valid signature is not itself a trust grant and never bypasses permission
policy.

Publisher authenticity and repository authenticity may both participate in the
broader supply-chain system; repository metadata is outside the `.lbp` byte
container specified here.

---

## 15. Canonical installation boundary

`luna-app-manager` owns Bundle installation.

The safe minimum sequence is:

```text
read
 ↓
validate header
 ↓
validate section table
 ↓
verify section hashes
 ↓
parse + validate manifest
 ↓
validate payload
 ↓
verify ContentIdentity
 ↓
verify signature when present
 ↓
Security / trust decision
 ↓
stage
 ↓
atomic commit
```

A failed extraction MUST leave no partially registered installed Bundle.

The `.lbp` file itself does not have to remain after installation.

---

## 16. Update and version interaction

A new version is installed as a separate immutable Bundle:

```text
BundleId = same logical identity
Version = different
ContentIdentity = normally different
```

Existing versions are never mutated as a side effect of installing a new version.
Retention/removal is managed by application/update policy.

Delta updates are explicitly outside RFC-0002.

---

## 17. External/removable media

External `.lbp` files may be inspected and, subject to policy, launched without
being copied into the installed application registry.

Discovery MUST NOT imply execution.

The conceptual flow is:

```text
DISCOVERED
   ↓
INSPECTED
   ↓
INTEGRITY VERIFIED
   ↓
SIGNATURE CHECKED (if present)
   ↓
TRUST DECISION
   ↓
AUTHORIZATION
   ↓
LAUNCH / INSTALL
```

---

## 18. Compatibility and versioning

### 18.1 Major version

A reader encountering an unknown major format version MUST reject the Bundle.

### 18.2 Minor evolution

Within a future compatible minor revision, unknown non-required metadata may be
ignored only when the reader can preserve all required semantics. Unknown required
semantics MUST reject.

### 18.3 Flags and sections

Unknown mandatory flags and unknown section types are rejected by v1. A future
format revision can explicitly redefine this rule.

### 18.4 Architecture

`platform.arch` is mandatory. Unsupported architecture values MUST be rejected.

---

## 19. Security and parser hardening

Readers and writers MUST protect against:

- integer overflow;
- out-of-bounds section ranges;
- overlapping sections;
- truncation;
- corrupt compressed streams;
- excessive decompression/resource consumption;
- traversal;
- absolute payload paths;
- duplicate paths;
- unsupported TAR entries;
- malformed TOML;
- invalid dependency constraints;
- invalid signature encodings.

Parser/resource limits are implementation policy rather than an artificial
format-wide maximum Bundle size.

Extraction MUST happen only after structural validation and required integrity
checks have succeeded.

---

## 20. Implementation ownership

### `luna-bundle`

Owns:

- Bundle representation;
- manifest schema and codec;
- RFC-0002 `.lbp` reader/writer;
- deterministic payload codec;
- integrity calculation;
- signature codec/verification boundary;
- Bundle-format validation.

### `luna-app-manager`

Owns:

- install;
- removal;
- update procedure;
- `.deb` / `.rpm` ingestion;
- migration;
- Bundle registration;
- lifecycle operations around Bundles.

### `luna-security`

Owns authorization/trust policy.

### `luna-root-mapping`

Owns logical mapping semantics.

### `luna-namespace` / runtime

Owns Linux namespace materialization and execution environment.

## 21. Reference test matrix

The reference implementation MUST test at least:

### Container

- valid 64-byte header;
- bad magic;
- unsupported major version;
- unknown flags;
- invalid table bounds;
- overflow;
- section overlap;
- section outside file;
- duplicate required sections;
- unknown section type.

### Manifest

- valid TOML round-trip;
- required-field validation;
- invalid Bundle ID/name;
- invalid SemVer;
- invalid type;
- missing application entry;
- logical path traversal;
- source path traversal/absolute path;
- duplicate mappings;
- unsupported architecture;
- unsupported dependency constraint.

### Payload

- deterministic output;
- round-trip extraction;
- traversal rejection;
- duplicate path rejection;
- symlink rejection;
- hard-link rejection;
- special-file rejection.

### Integrity

- header-hash mismatch;
- section-hash mismatch;
- decompression failure;
- ContentIdentity mismatch.

### Signature

- valid Ed25519 signature;
- invalid signature;
- unknown algorithm;
- absent optional signature;
- signed-material mismatch.

---

## 22. Rejected alternatives

### Plain `tar.zst` as `.lbp`

Rejected as the outer format. TAR remains useful as the deterministic PAYLOAD
encoding, while the dedicated outer header/section table provides manifest-first
inspection, per-section integrity and a clean signature boundary.

### Symlink-rich payloads

Rejected in v1 because safe link resolution adds substantial canonicalization and
security complexity. A later RFC may add explicitly constrained relative symlinks.

### Special filesystem entries

Rejected in v1 because Bundles do not need to create devices, sockets or FIFOs.

### Delta data inside `.lbp`

Rejected because delta transport is an update concern, not Bundle representation.

---

## 23. Acceptance record

The following decisions were explicitly accepted during the final RFC-0002 review:

- fixed 64-byte `LBP1` header;
- little-endian integer encoding;
- 64-byte fixed section entries;
- mandatory MANIFEST and PAYLOAD;
- optional RESOURCES and SIGNATURE;
- BLAKE3-256 for integrity and ContentIdentity;
- TOML manifest;
- `application` and `component` Bundle types;
- SemVer `MAJOR.MINOR.PATCH`;
- deterministic TAR payload;
- ZSTD canonical compression policy;
- logical mapping declarations in the manifest;
- mapping declarations are not authorization grants;
- no physical `DATA/...` mapping paths;
- no symlinks, hard links or special entries in v1;
- immutable installed Bundles;
- independent coexisting application versions;
- optional Ed25519 Bundle signature;
- signature, trust and permission remain separate;
- unknown major versions reject;
- unsafe/malformed containers fail closed;
- parser/resource limits remain implementation policy;
- delta updates remain outside RFC-0002.

**RFC-0002: Accepted.**

Changes to the normative Bundle Format v1 defined by this document require a new
RFC revision or superseding RFC.
