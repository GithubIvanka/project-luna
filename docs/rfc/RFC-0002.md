# RFC-0002: Формат Bundle v1 (`.lbp`)

| Field | Value |
|-------|-------|
| RFC | 0002 |
| Название | Формат Bundle v1 (`.lbp`) |
| Статус | **Принят** |
| Supersedes | — |
| Superseded by | — |
| Связанные документы | RFC-0001 (Architecture Baseline); спецификация System Image; модель безопасности |
| Источник истины | `docs/ARCHITECTURE.md` |
| Лицензия | Apache-2.0 |
| Принят | 2026-08-30 |

> **Примечание об авторитете.** Этот документ фиксирует решения, принятые для Bundle Format v1 в ходе Phase 1.6. Формат `.lbp` является transport/archive-представлением Luna Bundle. Он не является форматом System Image и не является runtime-представлением установленного приложения.

---

## 1. Аннотация

RFC-0002 определяет **Bundle Format v1** — формат `.lbp` для transport/archive-представления application и component bundles Project Luna.

Формат намеренно отделён от:

- формата System Image на основе SquashFS;
- хранения установленных неизменяемых Bundles;
- состояния runtime приложения;
- транзакций обновления;
- принудительного применения Security разрешений.

Формат v1 предоставляет детерминированный самодостаточный внешний контейнер с TOML manifest, детерминированным payload, hash целостности для каждой секции и необязательной секцией Ed25519 signature.

---

## 2. Цели

Bundle Format v1 ДОЛЖЕН:

1. однозначно идентифицировать свой формат;
2. позволять проверять manifest до извлечения payload;
3. предоставлять детерминированное представление, пригодное для стабильной идентичности содержимого;
4. обнаруживать повреждение и некорректные метаданные секций до установки;
5. предотвращать path traversal и небезопасные специальные entries архива;
6. поддерживать декларации логического mapping без раскрытия физических путей `LUNA-DATA/...`;
7. поддерживать запрошенные capabilities без выдачи разрешений;
8. позволять неизменяемым установленным Bundles сосуществовать в разных версиях;
9. поддерживать необязательную подлинность через Ed25519 без смешения signature, trust и authorization.

---

## 3. Вне целей

Этот RFC не определяет:

- структуру System Image или генерацию SquashFS;
- построение namespace;
- orchestration lifecycle приложения;
- применение Security policy;
- транзакции update/rollback;
- протокол discovery repository;
- протокол delta updates;
- формат резервного копирования пользовательских данных;
- окончательный синтаксис CLI `luna`.

---

## 4. Связь с хранилищем Luna

`.lbp` является **транспортным артефактом**.

```text
.lbp
  ↓ inspect / verify / trust
Bundle
  ↓ install
LUNA-DATA/system/apps/...
```

Payload установленного Bundle является неизменяемым. Конфигурация пользователя, пользовательские данные и
cache остаются вне payload и следуют установленному в Luna разделению DATA.

Внешний Bundle может быть запущен со съёмного носителя после inspection, проверки целостности и применимого решения trust/authorization. Его идентичность не зависит от имени файла или физического расположения.

System Images являются независимыми артефактами SquashFS и никогда не кодируются как `.lbp`.

---

## 5. Терминология и идентичность

### 5.1 Идентичность Bundle

Представление v1 содержит:

```text
BundleId
Version
ContentIdentity
```

`BundleId` — типизированная идентичность Luna для идентификации application/Bundle.

`Version` использует Semantic Versioning:

```text
MAJOR.MINOR.PATCH
```

`ContentIdentity` — это BLAKE3-256-дайджест канонического содержимого Bundle, определённого
by section 12.

Имя файла `.lbp` и физическое расположение не входят в идентичность.

### 5.2 Сосуществование версий

Разные версии одного приложения являются независимыми неизменяемыми Bundles.
Они могут сосуществовать и запускаться независимо, если в остальном совместимы с
политикой runtime Luna.

---

## 6. Внешний контейнер

#### 6.1 Порядок байтов

Все целочисленные поля кодируются в формате **little-endian**.

#### 6.2 Фиксированный заголовок

Заголовок имеет размер ровно **64 байта**:

| Offset | Size | Field | Meaning |
|-------:|-----:|-------|---------|
| `0` | 4 | `magic` | ASCII `LBP1` |
| `4` | 2 | `version_major` | currently `1` |
| `6` | 2 | `flags` | v1 MUST be `0` |
| `8` | 4 | `section_count` | number of section entries |
| `12` | 8 | `section_table_offset` | absolute file offset |
| `20` | 8 | `section_table_length` | table length in bytes |
| `28` | 4 | `header_length` | MUST be `64` |
| `32` | 32 | `header_hash` | BLAKE3-256 of header with this field zeroed |

`version_major` является major-версией формата. Будущий механизм minor-версии формата
не кодируется отдельным целым полем заголовка в v1; совместимая эволюция регулируется
правилами раздела 18.

Парсер ДОЛЖЕН отклонять неверный magic, неподдерживаемую major-версию, ненулевые неизвестные
flags, неверную длину заголовка, некорректные координаты таблицы и арифметическое переполнение.

#### 6.3 Фиксированные записи секций

Каждая запись секции имеет размер ровно **64 байта**:

| Offset | Size | Field |
|-------:|-----:|-------|
| `0` | 4 | `section_type` |
| `4` | 4 | `compression` |
| `8` | 8 | `offset` |
| `16` | 8 | `compressed_length` |
| `24` | 8 | `uncompressed_length` |
| `32` | 32 | `content_hash` |

Известные типы секций:

```text
1 = MANIFEST
2 = PAYLOAD
3 = RESOURCES
4 = SIGNATURE
```

Section rules:

| Section | Required | Compression |
|---------|----------|-------------|
| `MANIFEST` | exactly one | `NONE` |
| `PAYLOAD` | exactly one | `NONE` or `ZSTD` |
| `RESOURCES` | at most one | `NONE` or `ZSTD` |
| `SIGNATURE` | at most one | `NONE` |

Неизвестные типы секций отклоняются в v1. Unknown sections can only become
совместимой с будущим форматом только после явного назначения
semantics.

Диапазоны секций НЕ ДОЛЖНЫ пересекаться друг с другом или с областью заголовка/таблицы.

#### 6.4 Целостность секций

`content_hash` является BLAKE3-256 от сохранённых байтов секции в
контейнере до распаковки. Читатель ДОЛЖЕН проверить его до предоставления
декодированного содержимого секции.

---

## 7. Сжатие

v1 определяет:

```text
0 = NONE
1 = ZSTD
```

Каноническая политика записи:

```text
MANIFEST  → NONE
PAYLOAD   → ZSTD
RESOURCES → ZSTD when present
SIGNATURE → NONE
```

Средство записи, создающее канонический Bundle, ДОЛЖНО использовать эту политику. A non-canonical
транспортная копия может использовать `NONE` для `PAYLOAD`/`RESOURCES`, если семантическое содержимое Bundle
остаётся неизменным; парсер всё равно должен проверять сохранённые байты, а
канонический ContentIdentity должен вычисляться независимо от транспортного сжатия.

---

## 8. Манифест

Manifest обязателен и записывается в TOML.

Canonical structure:

```toml
format = 1

[bundle]
id = "org.example.firefox"
name = "Firefox"
version = "141.0.0"
type = "application"

[platform]
arch = "x86_64"
min_system = "1.0.0"

[entry]
exec = "bin/firefox"
logical = "/usr/bin/firefox"

[[dependency]]
id = "org.luna.libs.gtk"
version = "^4.0.0"

[capabilities]
requested = ["network", "clipboard"]

[[mapping]]
logical = "/usr/bin/firefox"
source = "bin/firefox"
access = ["execute"]

[metadata]
author = "Example"
license = "MPL-2.0"
homepage = "https://example.org"
```

### 8.1 Обязательные поля

Обязательны:

```text
format
bundle.id
bundle.name
bundle.version
bundle.type
platform.arch
```

Application Bundles требуют `[entry]` и `entry.exec`.

### 8.2 Типы Bundle

v1 permits:

```text
application
component
```

Неизвестные типы отклоняются.

System Images не являются типами Bundle.

### 8.3 Ограничения зависимостей

Ограничения версий зависимостей используют ограниченную грамматику SemVer, реализованную
Luna. Неподдерживаемый синтаксис ДОЛЖЕН отклоняться, а не угадываться.

### 8.4 Неизвестные поля

Неизвестные поля manifest могут сохраняться/игнорироваться when they do not introduce an
неизвестного обязательного семантического значения. Неизвестная обязательная семантика и неподдерживаемые
перечислимые значения ДОЛЖНЫ приводить к отклонению.

---

## 9. Логические отображения и capabilities

Mappings являются декларациями логического интерфейса Bundle, а не выдачей
разрешений.

```toml
[[mapping]]
logical = "/usr/bin/firefox"
source = "bin/firefox"
access = ["execute"]
```

Manifest НЕ ДОЛЖЕН содержать физические пути хранения Luna, такие как
`LUNA-DATA/system/apps/...` or `LUNA-DATA/users/...` as mapping targets.

`logical` is a Linux-style absolute логический путь. `source` является относительным к Bundle
путём. Обход каталогов и абсолютные пути, зависящие от host, недействительны.

Необязательное поле `access` описывает запрошенную семантику доступа. Final
authorization выполняется через `luna-security` и механизм принудительного применения runtime.

Запрошенные capabilities также являются только запросами:

```toml
[capabilities]
requested = ["network", "clipboard"]
```

Наличие декларации capability никогда само по себе не выдаёт эту capability.

---

## 10. Зависимости и общие библиотеки

Bundle может объявлять зависимости без встраивания payload этих зависимостей.
Ссылки на зависимости могут разрешаться из совместимых ресурсов самого Bundle,
`LUNA-DATA/system/libs` или других одобренных источников зависимостей.

Разрешением зависимостей владеют инструменты приложения/установки, not by the
`.lbp` parser itself.

Выбор shared libraries и физическое хранение находятся вне этого RFC; the manifest
выражает только логический контракт зависимостей.

---

## 11. Payload

`PAYLOAD` содержит дерево файлов Bundle как детерминированный TAR-поток, optionally
сжатый согласно разделу 7.

Разрешённые TAR entries:

- обычные файлы;
- каталоги.

Запрещено в v1:

- символические ссылки;
- жёсткие ссылки;
- FIFO;
- сокеты;
- символьные/блочные устройства;
- другие специальные типы записей.

Пути payload ДОЛЖНЫ быть относительными, каноническими, не допускающими обхода и ограниченными
Bundle payload root. Дублирующиеся пути payload отклоняются.

Явные записи каталогов являются необязательными.

---

## 12. Детерминированность и ContentIdentity

Построение canonical payload ДОЛЖНО:

1. детерминированно перечислять записи;
2. сортировать записи лексикографически по каноническому относительному пути Bundle;
3. использовать детерминированные метаданные TAR;
4. использовать `uid = 0` и `gid = 0`, если будущая редакция не определит иное;
5. use canonical `mtime = 0`;
6. не включать специфичные для host имена пользователя/группы и метаданные устройств;
7. не включать временные метки доступа/изменения;
8. порождать идентичные байты payload для идентичного содержимого Bundle.

Байты manifest, используемые для идентичности/подписи, ДОЛЖНЫ использовать каноническую сериализацию TOML.
Различия форматирования семантически эквивалентных manifest НЕ ДОЛЖНЫ создавать
несколько канонических идентичностей.

`ContentIdentity` is:

```text
BLAKE3-256(
    canonical_manifest
    || canonical_payload
    || canonical_resources_if_present
)
```

Она не включает имя `.lbp`, физическое расположение, транспортное заполнение и байты подписи.
bytes.

Поэтому `ContentIdentity` не изменяется при переименовании файла `.lbp` или
перемещении его на другое устройство хранения.

---

## 13. Секция ресурсов

`RESOURCES` необязательна и предназначена для ресурсов Bundle, представление которых
целесообразнее отделять от основного payload исполняемых файлов/дерева.

Её точный семантический реестр ресурсов определяется реализацией в v1 при условии, что
её байты участвуют в ContentIdentity и подчиняются тем же правилам безопасности путей и
целостности. Bundle не обязан иметь секцию RESOURCES, если все ресурсы
помещаются в PAYLOAD.

---

## 14. Подпись

Секция `SIGNATURE` является необязательной.

v1 определяет **Ed25519** для подписей Bundle.

Запись подписи содержит:

```text
algorithm
key_id
publisher_id
signature
```

Подписываемыми данными является каноническое представление Bundle:

```text
canonical header
+
canonical section table
+
canonical MANIFEST bytes
+
PAYLOAD content identity
+
RESOURCES content identity, if present
```

Секция SIGNATURE исключается из собственных подписываемых данных.

Отсутствие подписи допустимо на уровне формата. Whether an unsigned Bundle can
может ли Bundle быть установлен или запущен, определяется trust policy Luna.

Корректная подпись сама по себе не является выдачей trust и никогда не обходит policy
разрешений.

Подлинность издателя и репозитория могут обе участвовать in the
более широкой системе supply chain; метаданные репозитория находятся вне байтового
контейнера, определённого здесь.

---

## 15. Каноническая граница установки

`luna-app-manager` владеет установкой Bundle.

Безопасная минимальная последовательность:

```text
read
 ↓
validate header
 ↓
validate section table
 ↓
verify section hashes
 ↓
parse + validate manifest
 ↓
validate payload
 ↓
verify ContentIdentity
 ↓
verify signature when present
 ↓
Security / trust decision
 ↓
stage
 ↓
atomic commit
```

Неудачное извлечение НЕ ДОЛЖНО оставлять частично зарегистрированный установленный Bundle.

Сам файл `.lbp` не обязан сохраняться после установки.

---

## 16. Взаимодействие обновлений и версий

Новая версия устанавливается как отдельный неизменяемый Bundle:

```text
BundleId = same logical identity
Version = different
ContentIdentity = normally different
```

Существующие версии никогда не изменяются as a side effect of installing a new version.
Retention/removal is managed by application/update разрешений.

Дельта-обновления явно находятся вне RFC-0002.

---

## 17. Внешние и съёмные носители

Внешние `.lbp` файлы могут проверяться и, согласно policy, запускаться без
копирования в реестр установленных приложений.

Обнаружение НЕ ДОЛЖНО означать выполнение.

Концептуальный поток:

```text
DISCOVERED
   ↓
INSPECTED
   ↓
INTEGRITY VERIFIED
   ↓
SIGNATURE CHECKED (if present)
   ↓
TRUST DECISION
   ↓
AUTHORIZATION
   ↓
LAUNCH / INSTALL
```

---

## 18. Совместимость и версионирование

### 18.1 Major-версия

Reader, встретивший неизвестную major-версию формата, ДОЛЖЕН отклонить Bundle.

### 18.2 Эволюция minor-версии

В будущей совместимой minor-редакции неизвестные необязательные метаданные могут
игнорироваться только если читатель способен сохранить всю обязательную семантику. Неизвестная обязательная
semantics MUST reject.

### 18.3 Flags и секции

Неизвестные обязательные flags и типы секций отклоняются в v1. A future
редакция формата может явно переопределить это правило.

### 18.4 Архитектура

`platform.arch` обязателен. Неподдерживаемые значения архитектуры ДОЛЖНЫ отклоняться.

---

## 19. Безопасность и защита parser

Читатели и средства записи ДОЛЖНЫ защищаться от:

- integer overflow;
- out-of-bounds section ranges;
- overlapping sections;
- truncation;
- corrupt compressed streams;
- excessive decompression/resource consumption;
- traversal;
- absolute payload paths;
- duplicate paths;
- unsupported TAR entries;
- malformed TOML;
- invalid dependency constraints;
- invalid signature encodings.

Ограничения парсера/ресурсов являются политикой реализации, а не искусственным
глобальным ограничением размера Bundle на уровне формата.

Извлечение ДОЛЖНО выполняться только после структурной проверки и необходимых проверок целостности
успешно завершены.

## 21. Эталонная матрица тестов

Эталонная реализация ДОЛЖНА проверять как минимум:

### Контейнер

- valid 64-byte header;
- bad magic;
- unsupported major version;
- unknown flags;
- invalid table bounds;
- overflow;
- section overlap;
- section outside file;
- duplicate required sections;
- unknown section type.

### Манифест

- valid TOML round-trip;
- required-field validation;
- invalid Bundle ID/name;
- invalid SemVer;
- invalid type;
- missing application entry;
- logical path traversal;
- source path traversal/absolute path;
- duplicate mappings;
- unsupported architecture;
- unsupported dependency constraint.

### Payload

- deterministic output;
- round-trip extraction;
- traversal rejection;
- duplicate path rejection;
- symlink rejection;
- hard-link rejection;
- special-file rejection.

### Целостность

- header-hash mismatch;
- section-hash mismatch;
- decompression failure;
- ContentIdentity mismatch.

### Подпись

- valid Ed25519 signature;
- invalid signature;
- unknown algorithm;
- absent optional signature;
- signed-material mismatch.

## 22. Отклонённые альтернативы

### Обычный `tar.zst` как `.lbp`

Отклонено как внешний формат. TAR остаётся полезным как детерминированное кодирование PAYLOAD,
а специальный внешний заголовок/таблица секций обеспечивают проверку manifest прежде
извлечения, целостность по секциям и чёткую границу подписи.

### Payload с большим количеством symlink

Отклонено в v1, поскольку безопасное разрешение ссылок добавляет существенную сложность каноникализации и
безопасности. Более поздний RFC может добавить явно ограниченные относительные symlinks.

### Специальные filesystem entries

Отклонено в v1, поскольку Bundles не должны создавать устройства, сокеты или FIFO.

### Delta-данные внутри `.lbp`

Отклонено, поскольку delta transport относится к обновлениям, а не к представлению Bundle.

---

## 23. Запись о принятии

Следующие решения были явно приняты в ходе финального рассмотрения RFC-0002:

- fixed 64-byte `LBP1` header;
- little-endian integer encoding;
- 64-byte fixed section entries;
- mandatory MANIFEST and PAYLOAD;
- optional RESOURCES and SIGNATURE;
- BLAKE3-256 for integrity and ContentIdentity;
- TOML manifest;
- `application` and `component` Bundle types;
- SemVer `MAJOR.MINOR.PATCH`;
- deterministic TAR payload;
- ZSTD canonical compression policy;
- logical mapping declarations in the manifest;
- mapping declarations are not authorization grants;
- no physical `LUNA-DATA/...` mapping paths;
- no symlinks, hard links or special entries in v1;
- immutable installed Bundles;
- independent coexisting application versions;
- optional Ed25519 Bundle signature;
- signature, trust and permission remain separate;
- unknown major versions reject;
- unsafe/malformed containers fail closed;
- parser/resource limits remain implementation policy;
- delta updates remain outside RFC-0002.

**RFC-0002: Accepted.**

Изменения нормативного Bundle Format v1, определённого этим документом, требуют новой
редакции RFC или заменяющего RFC.
