## 2. Repository and implementation policy

The repository follows current architecture rather than historical component names. Empty future crates are not created merely to reserve names. A component is added when its responsibility and API boundary are sufficiently defined.

Existing code is source material, not an automatic architectural commitment.

`luna-common` remains a small foundation crate. Subsystem-specific errors, policies, runtime state, filesystem operations, bundle semantics and service APIs belong to their owning crates.

Where a component needs reusable library functionality plus a process/service boundary, the accepted shape is **bin + lib** where appropriate.

Tokio is the accepted async runtime direction where an async runtime is actually needed; this does not require every crate to depend on Tokio.

## 3. Accepted decisions 1.6-1 → 1.6-40

1. **1.6-1:** Linux-style logical paths use lexical normalization followed by secure physical resolution; `..` cannot escape the authorized root and symlink traversal requires boundary validation.
2. **1.6-2:** Mapping fallback is semantic-class-specific; no universal filesystem search chain.
3. **1.6-3:** Application security identity is based on `BundleId`; version is additional context.
4. **1.6-4:** Different application versions are independent immutable runtime resources.
5. **1.6-5:** Full event stack: Event → Bus → history where appropriate → subscribers/replay; Kafka is conceptual only.
6. **1.6-6:** `luna-state` represents logical persistent state; checkpoint/rollback is separate; Btrfs is an implementation option only.
7. **1.6-7:** `luna-app-manager` produces/validates `ApplicationPlan`; `luna-update-manager` executes changes.
8. **1.6-8:** `luna-system-runtime` creates/supervises UserSessions; no separate Session Manager.
9. **1.6-9:** system-runtime is the global authority for `ApplicationInstanceId` uniqueness.
10. **1.6-10:** Resource protection is current implementation work using Linux resource-control mechanisms initially.
11. **1.6-11:** First app isolation uses mount namespaces + controlled bind mounts + Root Mapping, with OverlayFS where useful; custom VFS deferred to a future major version.
12. **1.6-12:** System State, Boot State and Recovery State remain separate; Recovery State is RAM-only.
13. **1.6-13:** Logical paths are Linux-style absolute paths.
14. **1.6-14:** Physical paths remain internal; user-facing navigation exposes Luna DATA and friendly volumes.
15. **1.6-15:** File mappings are default; explicit directory/subtree mappings are allowed for suitable semantic classes such as libraries.
16. **1.6-16:** Each application namespace has its own RAM-resident mapping table.
17. **1.6-17:** Identical immutable mapping definitions may be safely shared; namespace-specific state remains isolated.
18. **1.6-18:** Different applications may map the same logical dependency path to different physical versions without conflict.
19. **1.6-19:** Mapping conflict in one namespace is an error.
20. **1.6-20:** System is lowest fallback precedence where fallback applies.
21. **1.6-21:** Application resources may shadow lower defaults where permitted.
22. **1.6-22:** User overrides may shadow lower defaults where permitted.
23. **1.6-23:** User → application → system precedence is semantic-class-specific.
24. **1.6-24:** Security is checked before final MappingPlan acceptance.
25. **1.6-25:** Application cannot mutate its active MappingTable after namespace creation.
26. **1.6-26:** app-runtime consumes validated MappingPlan and does not invent mappings.
27. **1.6-27:** root-mapping does not own application lifecycle.
28. **1.6-28:** ApplicationPlan belongs to app-manager.
29. **1.6-29:** UpdatePlan belongs to update-manager.
30. **1.6-30:** Plans do not contain low-level mount/syscall details.
31. **1.6-31:** A high-level operation may contain multiple targets and per-target status where transactional semantics permit.
32. **1.6-32:** Managers remain owners of their domain state.
33. **1.6-33:** system-runtime is ApplicationInstanceId authority.
34. **1.6-34:** Global uniqueness is not separately generated by per-user app-runtimes.
35. **1.6-35:** app-runtime owns individual ApplicationInstance lifecycle after creation.
36. **1.6-36:** Hierarchy is `system-runtime → UserSession → app-runtime`.
37. **1.6-37:** UserSession contains user identity, state and resource/policy context.
38. **1.6-38:** app-runtime does not create UserSessions.
39. **1.6-39:** Recovery uses temporary identity, not normal persistent UserSession.
40. **1.6-40:** Recovery uses RAM-backed state and explicit authorization before protected user data is opened.

## 4. Accepted decisions 1.6-41 → 1.6-75

41. `luna-fs` owns low-level filesystem paths, not LogicalPath domain semantics.
42. PhysicalPath belongs to mapping/storage, not common.
43. `luna-fs` supports files, directories, metadata, symlinks and mode metadata without deciding authorization.
44. Filesystem errors are local to `luna-fs`; no global LunaError.
45. root-mapping exposes typed logical/physical domain concepts.
46. MappingTable supports insert/remove/lookup/conflict detection/validation.
47. Validated MappingTable is immutable after runtime handoff; changes produce a new table/version.
48. Immutable tables permit atomic replacement.
49. Validated MappingPlan is immutable.
50. Security-policy changes can require MappingPlan revalidation.
51. Security policy is revisioned.
52. Grants may be one-time, operation-scoped, while-running or persistent.
53. Security owns policy/grants/trust, not runtime process state.
54. Trust binds BundleId, content identity/hash and scope.
55. Trust is content-specific.
56. Bundle resources are typed domain objects.
57. Manifest separates identity/metadata/resources/dependencies/capabilities/entry points; runtime state is excluded.
58. ApplicationInstanceId is not manifest data.
59. UserSessionId is not manifest data.
60. Immutable Bundles are reusable across UserSessions.
61. luna-bundle does not own physical installation paths.
62. app-manager constructs/validates ApplicationPlan without launching apps.
63. ApplicationPlan validates dependencies/compatibility/security/resources/migrations before execution.
64. Invalid plans cannot enter mutation.
65. UpdatePlan belongs to update-manager.
66. Update stages are prepare/checkpoint/apply/verify/commit.
67. Old state remains authoritative before commit where possible.
68. Reconciliation determines committed/partially committed/not committed after interruption.
69. Rollback is explicit, not automatic for every crash.
70. luna-state may reference checkpoints but does not own snapshot internals.
71. Events carry correlation metadata.
72. Live subscriptions are separate from persistent event history.
73. Subscriptions have explicit lifecycle.
74. GUI/CLI disconnect does not cancel backend operations or erase operation state.
75. **Option C:** luna-state contains state domain plus storage traits/backend implementations; checkpoint remains separate and state remains backend-agnostic.

## 5. Accepted decisions 1.6-76 → 1.6-115

76. `luna-state` uses synchronous storage; async orchestration is higher-layer work.
77. State storage supports minimal atomic transactions.
78. Revision-based optimistic concurrency is supported.
79. EventId and OperationId are independent.
80. Event ordering is monotonic per operation; no global total order across independent operations.
81. Timestamp is metadata, not ordering.
82. Event classes are Ephemeral, Persistent and Audit.
83. Persistent event history supports replay/query.
84. Event delivery uses bounded queues/backpressure.
85. Overflow handling is class-specific; Audit events cannot be silently dropped.
86. Interrupted operations are reconciled after service/runtime recovery.
87. Operations distinguish resumable/non-resumable/unknown where necessary.
88. Operations belong to System or UserSession context, not GUI/CLI processes.
89. Operation authorization distinguishes view/cancel/resume/rollback.
90. Force Stop is distinct from cooperative Cancel and requires stronger/emergency authorization with warning where applicable.
91. Bundle logical paths use a dedicated validated domain type.
92. Bundle-relative source paths use a dedicated domain type.
93. Bundle resources carry explicit resource types/metadata.
94. Conflicting same-logical-path mappings within a namespace are errors.
95. Exact duplicate resource entries may be deduplicated; distinct targets remain a conflict.
96. Bundle identity is BundleId + Version + ContentIdentity.
97. ContentIdentity is independent of filename and physical storage location.
98. Moving a Bundle does not change its identity.
99. External Bundle flow is inspect → verify → trust decision → launch; no implicit execution.
100. Permissions distinguish Visibility, Read, Write, Execute, DeviceUse and Manage.
101. Application-level restrictions propagate to all instances of that application identity.
102. An instance may tighten but not weaken application policy.
103. Security policy revision participates in revalidation.
104. Ask means explicit user/system confirmation is required; Security remains UI-agnostic.
105. Constrained returns structured typed restrictions.
106. ApplicationInstance lifecycle distinguishes Created/Starting/Running/Stopping/Stopped/Crashed/Failed.
107. system-runtime detects and may restart failed app-runtime without automatically terminating UserSession.
108. Runtime metadata recovery does not imply application process-memory restoration.
109. system-runtime restart is preferred over unnecessary full-machine reboot where recovery is possible.
110. A protected system-critical resource budget is reserved.
111. Resource reservation is adaptive rather than a universal fixed percentage.
112. Memory-pressure reclamation is ordered from disposable/reclaimable resources toward application pressure/termination, while system-critical memory remains protected.
113. GUI and CLI use shared backend contracts and do not directly operate on filesystem/runtime internals.
114. `luna` supports machine-readable output in addition to human-readable output; exact syntax remains CLI specification.
115. Public internal component contracts have explicit compatibility versions; breaking changes require major changes and incompatible clients are explicitly rejected.

## 6. Rejected/corrected audit proposals

- `resolver = "3"` → `resolver = "2"` was rejected. Resolver v3 is stable and appropriate for Rust 2024; Rust 1.84 stabilized it, and Rust 2024 implies resolver v3. 
- `SystemState.previous` as the complete fallback model was rejected; fallback uses inventory and compatibility queries and is not limited to one previous image.
- Raw host `PathBuf` as the universal BundleResource domain representation was rejected; Bundle uses dedicated logical/source path types.
- Mandatory `into_string()` on every wrapper was rejected as an architectural rule.
- Mandatory `const fn` everywhere technically possible was rejected as an architectural/style rule.
