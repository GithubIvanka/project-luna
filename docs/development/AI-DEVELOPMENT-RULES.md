# Project Luna — Правила разработки с участием ИИ

**Статус:** правила разработки
**Основание:** `docs/ARCHITECTURE.md`, принятые решения и контракты компонентов

## 1. Язык документации

Все описания Project Luna должны быть написаны **на русском языке**.

Это относится к:

- архитектуре;
- компонентам и их контрактам;
- README;
- инструкциям по сборке;
- описанию зависимостей;
- состоянию реализации;
- планам и диагностическим документам.

Без перевода допускаются имена файлов, crate, функций, типов, программ, команд и официальные названия внешних проектов.

## 2. Обязательное чтение

Перед изменением компонента ИИ обязан изучить:

1. `docs/ARCHITECTURE.md`;
2. `docs/decisions/ACCEPTED-DECISIONS.md`;
3. документ компонента в `docs/architecture/components/`;
4. связанные RFC/ADR;
5. карту crate и API-контрактов;
6. текущий код и тесты.

Исторические документы можно использовать для traceability, но они не заменяют текущий SoT.

## 3. Запрет архитектурных галлюцинаций

Нельзя придумывать новый Luna-компонент, crate, daemon, session manager, persistent directory, протокол, API или ownership boundary только потому, что так удобнее реализовать код.

Linux-утилита или сторонний daemon не становится Luna-компонентом автоматически.

## 4. Владение

Принятая модель обязательна:

```text
luna-system-runtime
├── UserSession A
│   ├── luna-app-runtime
│   └── GUI/Desktop session
└── UserSession B
    ├── luna-app-runtime
    └── GUI/Desktop session
```

`UserSession` — граница сессии. `luna-system-runtime` — единственный системный runtime/supervisor. `luna-app-runtime` — выполнение `ApplicationInstance`. Отдельного `luna-session`, `luna-runtime` или `luna-run-session` нет.

## 5. Статусы

Нужно различать:

- **Принято**;
- **Реализовано**;
- **Интеграция**;
- **Запланировано**;
- **Открытый вопрос**.

Нельзя выдавать planned/open за implemented.

## 6. Порядок работы

```text
контракт
 ↓
аудит текущего кода
 ↓
минимальное изменение внутри существующего owner
 ↓
тесты
 ↓
format/check/clippy/build
 ↓
архитектурная проверка diff
 ↓
commit
```

Если требуется изменение принятой архитектуры, сначала оформляется решение RFC/ADR.

## 7. Документация сборки обязательна

Для каждого компилируемого компонента его документация должна содержать:

- необходимые инструменты;
- минимальные требования и версии, когда они существенны;
- подготовку окружения;
- точную команду сборки;
- порядок шагов;
- расположение результата;
- команды проверки результата;
- тестовый сценарий;
- известные ошибки/предпосылки, если они уже встречались в проекте.

Разработчик не должен угадывать, что устанавливать и в каком порядке запускать команды.

## 8. Автоматизация сборки

Для повторяемых процедур должны существовать автоматические скрипты в `tools/`.

Минимальный набор:

- сборка отдельного компонента;
- тестирование отдельного компонента;
- сборка kernel;
- сборка desktop root;
- сборка полного PC-образа.

Скрипты должны проверять предпосылки до дорогостоящих операций и выдавать понятный путь к результату.

## 9. Честность

Нельзя считать подсистему интегрированной только из-за placeholder, конфигурации, wrapper или установленного пакета.

Например:

- упаковка Yazi не означает прямую интеграцию `yazi-core`;
- упаковка PipeWire/NetworkManager/BlueZ не означает готовый Luna provider;
- kernel build script не означает доказанный end-to-end boot;
- handoff-файл login не является окончательной authentication IPC архитектурой.

## 10. Тестирование и CI

Нужно проверять не только happy path, но и ownership/failure boundaries.

Перед утверждением, что CI зелёный, необходимо проверить результат именно для текущего commit.

При падении CI: определить шаг → изучить лог → воспроизвести по возможности → сделать минимальный исправляющий commit → повторно проверить.

## 11. Запрет обхода владельца

Нельзя добавлять обходной компонент, если работа уже принадлежит существующему owner.

Linux helper может использоваться внутри реализации существующего компонента, но не должен превращаться в новый архитектурный boundary без принятого решения.

## 12. Новая архитектурная граница

Перед предложением нового компонента нужно ответить:

1. Какое состояние он единолично владеет?
2. Почему существующий owner не может владеть этим состоянием?
3. Почему недостаточно API/library boundary?
4. Какой lifecycle появляется у нового компонента?
5. Какие зависимости ему нужны?
6. Какое принятое решение разрешает новую границу?

При отсутствии ответа новый компонент не создаётся.
