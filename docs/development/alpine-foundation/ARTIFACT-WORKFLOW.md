# Образы разработки и автоматическая очистка

Принято пользователем 2026-10-11: хранить два рабочих образа — принятый эталон
и эксперимент/предыдущий эталон; удалять старые временные диски автоматически.
Источник реализации: `tools/canonical-luna-workbench.py` и
`tools/canonical-luna-artifacts.py`.

## Два слота

`target/canonical-workbench/slots/a/` и `slots/b/` содержат по одному
`luna-0.1.0.img`. Роли записаны в `state.json`; имя слота не означает его роль.
После успешного полного проверочного прогона роли меняются атомарно. Прежний
эталон остаётся резервом до следующего эксперимента. Перед новым экспериментом
переиспользуется только неактивный слот. Неуспешный эксперимент эталоном не становится.

`evidence/<timestamp>/` хранит результаты, журналы сборки, последовательного порта
и QMP, а также сведения о замене ресурсов отдельно от образов. Обычный запуск
не накапливает новые полные образы диска. Снимок входных данных, артефакты
поставщиков ресурсов/графики и кэш Cargo переиспользуются. Эти кэши автоматически
вместе с образом не удаляются.

Один управляющий процесс владеет блокировкой. Проверочный прогон и копирующий `cp`
наследуют её: новый запуск не переиспользует слот, пока работает дочерний процесс,
оставшийся после аварии. При обычной отмене дерево проверочных процессов
останавливается до очистки. После получения блокировки следующий запуск удаляет
известные временные слои тестовых дисков из помеченных старых каталогов результатов.
Журналы и прочие файлы сохраняются.

## Команды

Первоначальный перенос уже принятого образа:

```sh
python3 tools/canonical-luna-workbench.py init \
  --image target/luna-alpha-stabilization-20261010/regression-final/image/luna-0.1.0.img \
  --results target/luna-alpha-stabilization-20261010/regression-final/results.txt \
  --inputs target/luna-alpha-stabilization-20261010/inputs-final
```

Эта команда уже выполнена в текущем рабочем каталоге; исходный дубликат после
проверки нового эталона удалён. Пример выше фиксирует историю импорта. В новом
рабочем каталоге первоначальный принятый образ получают обычной сборкой и полным
набором проверок с явно заданными каталогами результата, затем импортируют.
`init` требует итоговый PASS полного прогона, контрольную сумму исходного образа
и закреплённое описание входных данных. Неизвестное содержимое существующих
каталогов отклоняется.

Состояние и полноценная новая сборка:

```sh
python3 tools/canonical-luna-workbench.py status
# Для Alpha с desktop-bundles нужен проверенный независимый Wayland-бандл:
export LUNA_CANONICAL_WAYLAND_FIXTURE="$PWD/target/luna-alpha-design-20261013/wayland-fixture-delivery"
python3 tools/canonical-luna-workbench.py run build
# Та же управляемая сборка с полным проверочным прогоном:
bash tools/test-canonical-luna-regression.sh
# После подготовки нового неизменяемого снимка входных данных, например ядра:
python3 tools/canonical-luna-workbench.py run build --inputs /absolute/path/new-inputs
```

`LUNA_CANONICAL_WAYLAND_FIXTURE` указывает на подготовленный тестовый Weston
из `tools/prepare-luna-wayland-fixture.py`, соответствующий выбранному
`inputs.lock.json`. Для Alpha с `desktop-bundles` он обязателен: проверка
реального независимого Wayland-приложения является частью принятия. Указанный
путь существует в текущем рабочем каталоге; при выборе нового снимка нужно
подготовить соответствующий бандл. Workbench отклоняет отсутствие параметра
до переиспользования слота. Бандл устанавливается только во временный слой
проверки и не добавляется в поставляемый System Image или DATA.

Замена существующего ресурса загрузки/экрана входа без полной сборки:

```sh
python3 tools/canonical-luna-workbench.py run resources \
  --replace resources/fonts/JetBrainsMonoNerdFontMono-Regular.ttf /absolute/path/font.ttf
```

Можно повторять `--replace`. Инструмент копирует эталон в экспериментальный слот
через reflink — копию с общими неизменёнными блоками, если файловая система хоста
её поддерживает. Иначе выполняет разреженное копирование без выделения пустых
участков файла. Затем извлекаются только ext4 LUNA-SYS и небольшой System Image,
собирается новый SquashFS и записываются лишь изменившиеся блоки SYS.
EFI/GPT, ядро, `.init`, обычная DATA и DATA восстановления берутся из исходной копии.

Это изготовление нового **артефакта разработки**. Принятый образ неизменяем;
системные образы для установленной ОС также неизменяемы и имеют версии.
Инструмент не является средством обновления установленной ОС.

Разрешена замена только существующих обычных файлов в разделах ресурсов
System Image `apps`, `config`, `resources`, `libs`, `drivers`, `firmware`.
Символические ссылки, пути с обходом каталогов и устройства отклоняются.
Добавление ресурсов, смена ядра/init, контрактов загрузки, DATA, поставщиков
ресурсов, схемы данных или исходного Rust-кода требуют `run build`.
Новый снимок входных данных проверяется заранее и становится активным только
с принятой сборкой; при неуспешной сборке старый выбор сохраняется.
Сейчас поставщики рабочего стола находятся в DATA; режим замены ресурсов
их не обновляет.

Повторная проверка сохранённого неуспешного эксперимента: `run test`.
Его закреплённое описание входных данных сравнивается с выбранным снимком.
По умолчанию выбран снимок эталона. Для эксперимента с новыми входными данными
можно явно указать `run test --inputs /absolute/path/experiment-inputs`.
Снимок проверяется, а его описание должно точно совпадать с описанием кандидата.
Команда не меняет ядро или содержимое образа и не пересобирает его.
Несовпадение приводит к отказу до QEMU: нужен исходный снимок либо
`run build --inputs` с новым. Это исключает неверную привязку после неуспешной
сборки с другими входными данными. Снимки хранятся вне управляемых слотов,
чтобы смена ролей не могла их удалить.

Принятие эталона требует всех шагов набора проверок и итогового PASS;
контрольная сумма связывает результат с проверенными байтами. Обязательны также
проверки `app-runtime` и `bundle-launch`: установленное приложение должно пройти
настоящую пользовательскую сессию, ограничения пространства имён, очистку
потомков и сохранение данных. Образ, его контрольная сумма и итоговые результаты
синхронизируются на диск до публикации нового постоянного состояния.

## Временные данные

Для просмотра принятой Alpha в графическом окне:

```sh
python3 tools/canonical-luna-workbench.py view
# Обычное растягиваемое окно вместо полноэкранного режима:
python3 tools/canonical-luna-workbench.py view --windowed
```

Используются GTK/OpenGL с `zoom-to-fit`, USB tablet с абсолютными координатами
и принятый слот из `state.json`. По умолчанию окно полноэкранное. В GTK QEMU
`Ctrl+Alt+F` переключает полноэкранный режим. Сеанс удерживает блокировку
workbench до закрытия QEMU, чтобы сборка не заменила открытый слот. Изменения
гостя находятся в автоматически удаляемом snapshot-слое; состояние OVMF
также временное. Третьего постоянного образа нет. Команда, serial, журнал
QEMU и контрольная сумма исходного образа сохраняются в каталоге доказательств.

Проверки запуска бандлов, входа и жизненного цикла выполняются последовательно
на одном исходном образе, каждая — в небольшом временном слое qcow2. Сценарий
жизненного цикла меняет только System Image в своём слое. Загрузочные проверки
`production`/`display` используют режим QEMU snapshot. Диски удаляются как при
успехе, так и при обычном сбое; журналы сохраняются. После полного управляемого
прогона инструмент очищает `.build` и распакованные `luna-sys`/`luna-data`
в собственном слоте. Проверка структуры удаляет извлечённые ей разделы и деревья
при обработке EXIT.

Отдельная диагностика может использовать `LUNA_CANONICAL_KEEP_TEST_DISKS=1`;
после неё сохранённый временный слой удаляют отдельно. Управляемый запуск
принудительно использует `0`, чтобы обычные прогоны были ограничены по месту.
После SIGKILL или потери питания очистка при EXIT не гарантирована; остатки видны
в каталоге результатов, а эталон без завершённого PASS не принимается.

По умолчанию сборщик не экспортирует дополнительные распакованные копии SYS/DATA.
Для прямой диагностики: `LUNA_CANONICAL_EXPORT_TREES=1`. Автоматическая очистка
ограничена помеченными каталогами сгенерированного результата внутри `target`.
Исходники, пользовательские сценарии проверки, `.git`, снимки входных данных,
журналы и Graphify не входят в её область.

## Проверка и освобождённое место

Очистка 2026-10-11 освободила **97,08 GiB**: сначала 58 проверенных сгенерированных
артефактов (82,83 GiB), затем шесть старых исходных образов (14,25 GiB), после
полного принятия нового эталона и сверки контрольных сумм. Журналы, входные
снимки, исходники, пользовательские сценарии проверки и первоначальный образ
`target/luna-canonical-noctalia-20261010/luna-0.1.0.img` сохранены. Этот исторический
образ находится вне двух рабочих слотов и автоматической смены их ролей.

После той очистки `target` занимал около **20 GiB**, два разреженных рабочих
образа — **2,5 GiB** выделенных блоков, их результаты — **13 MiB**.
На файловой системе было свободно около **98 GiB** на момент измерения.
Это реально выделенные байты; логический размер образа больше, а полная сборка
может временно занимать дополнительное место. Точные результаты:
`target/luna-storage-audit-20261011/cleanup-result.json` и
`obsolete-image-cleanup-result.json`. Эти числа описывают историческое измерение,
а не текущее свободное место.

Проверки защиты и смены слотов: `python3 tools/test-canonical-luna-artifacts.py` —
**24 PASS**, включая отказ при несовпадении описания входных данных и размещении
снимков внутри очищаемых слотов. Полный прогон OVMF — **PASS**, результаты:
`target/canonical-workbench/evidence/20261011-123539-844060/results.txt`.
Проверены загрузка/видеопереход, три входа на рабочий стол, выход с повторным
входом, настоящие перезагрузка/выключение гостевой системы и сохранение
HOME/config/ревизии состояния. Тогда `b` стал эталоном, `a` — предыдущим
эталоном/экспериментом; текущие роли следует читать из `state.json`.

Эксперимент с ресурсом заменил тот же шрифт экрана входа: изменено
**262144 байта SYS**, DATA не пересобиралась. На хосте без reflink по-прежнему
нужна разреженная копия эталона; число изменённых блоков не равно полному объёму
операций чтения/записи. Эта историческая проверка управления артефактами
выполнялась на прежнем пользовательском стеке. Последующий запуск установленных
бандлов и его отдельная сборка описаны в
[LAUNCH-STAGE.md](../application-bundles/LAUNCH-STAGE.md).
